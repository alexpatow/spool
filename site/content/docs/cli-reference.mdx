Every `spool` command and option, generated from `spool <command> --help`. [Command line](/docs/cli) shows what each command does and prints.

## Options of many commands

### Output options

Every command that prints a result takes these. [Output](/docs/cli#output) shows each format.

- `-o, --output <OUTPUT>`: Output format. Default `table`. One of `table`, `json`, `ndjson`, `csv`.
- `--json`: Shorthand for `--output json`

### Server options

Every command that calls a running server takes these.

- `--url <URL>`: The server. Default `http://127.0.0.1:7765`. Falls back to `SPOOL_URL`.
- `--token <TOKEN>`: A token for that server; `spool dev` needs none. Falls back to `SPOOL_TOKEN`.

### Global options

Every command takes these.

- `--color <WHEN>`: When to use colour. Default `auto`. One of `auto`, `always`, `never`.

  `auto` uses it on a terminal, unless NO_COLOR is set, and where CLICOLOR_FORCE is. JSON, NDJSON and CSV never have colour.
- `-q, --quiet`: Print only the result and errors: no hints or progress

## spool init

Create a project, empty or from an example

Creates a project: the standard folders, a .gitignore and a .env.example. With --example, it's a complete project with sample rows and documents to load.

Runs git init if the folder has no repository. This requires Git on PATH and creates an empty repository with no commits.

Either way, it writes what coding agents read: AGENTS.md (imported by CLAUDE.md) and skills for using Spool, in .agents/skills/ with a symlink to each from .claude/skills/. `spool update-skills` updates them to a later version's.

The folder has to be empty apart from `.git` and `.DS_Store`. Otherwise it's refused and nothing is written.

Spool passes the variables in the project's .env to the extractors and strategies it runs, and never prints their values. Variables already set in Spool's environment win. Git ignores .env, and .env.example shows the format.

```text
spool init [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The folder to make the project in, made if it is not there [default: the current folder]

Options:

- `--example <NAME>`: Fill the project with an example. One of `companies`.

It takes the [output options](#output-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool init companies --example companies
spool init my-data
```

## spool info

List what a project declares, and check its SQL

Lists what the project directory declares: its sources, with the columns each has and the features each column becomes; its entity types, with their feature columns, their rules and their user-code strategies; and its extractors. Every SQL file is checked on the way.

What the records hold in those columns is on the server: `spool show attributes` says how many records have each and the values most have.

```text
spool info [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project directory [default: the current directory]

It takes the [output options](#output-options).

## spool dev

Run a server on localhost that applies file changes as they are saved

Runs a development server straight from a project directory, with its store under .spool/. Project files are applied as you save them. A change that doesn't compile is reported, and the last good version keeps running.

Open its address in a browser for the studio. There's no sign-in and no token: every change is recorded under an admin account called `dev`. That's why it only listens on, and answers, localhost. Use `spool serve` for a server other people reach. A caller that does send a token writes as that token.

Agents on this machine that speak the Model Context Protocol, such as Claude Code, connect at `/mcp`, with tools to load rows and documents, match, look things up and change identities.

Strategies and extractors run with `uv` for `.py` files and `bun` for `.ts` files. Set SPOOL_UV and SPOOL_BUN if they aren't on your PATH. They get the variables the project's .env sets, except those already set in the server's environment, and .env is reread each time one starts.

Ctrl-C stops it, as described in `spool serve --help`.

```text
spool dev [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project directory [default: the current directory]

Options:

- `--listen <ADDR>`: The loopback address to listen on. Default `127.0.0.1:7765`.
- `--store <PATH>`: The store's database file [default: `<DIR>/.spool/dev.duckdb`]

User code options:

- `--task-timeout <SECONDS>`: How long a user-code strategy or an extractor may run. Default `600`.
- `--tasks <DIR>`: Where the task directories of user code are made

  The default is `spool-tasks` in the temporary directory.

## spool add

Add one row and get its identity

Sends one row to a running server. The project's rules match its record against existing identities. A record that fits several identities is left for review, and the answer gives the review item.

```text
spool add [OPTIONS] --source <NAME> --type <NAME> <ROW>
```

Arguments:

- `<ROW>`: A JSON object of column values, or `-` to read it from standard input

Options:

- `--source <NAME>`: The source that supplies the row
- `--type <NAME>`: The entity type the row describes
- `--replace`: Allow a new version under an existing key

It takes the [output options](#output-options) and the [server options](#server-options).

## spool load

Send the rows of a file to a running server

Sends the rows of a CSV file to a running server, which keeps each row as a record. The first line of the file names the columns, and each has to be a column the source lists in its `sources/<name>.yaml`. Every value is text, and an empty field is a missing value.

Loading does not match: `spool match` places the records in identities. Loading the same rows again adds nothing. A row that comes again under the same key with other content is a new version of that row.

```text
spool load [OPTIONS] <FILE>
```

Arguments:

- `<FILE>`: The file to read; `-` reads standard input

  A file whose name ends in .tsv or .tab has tabs between its fields.

Options:

- `--source <NAME>`: The source the rows come from

  The default is the only source the project declares, the one the file is named after, as crm-1.csv is after `crm`, or else the one that lists most of the file's columns.
- `--type <NAME>`: The entity type they are records of [default: the only type whose mapping reads the source]
- `--delimiter <CHAR>`: The character between the fields, or `tab` [default: a comma, or a tab for .tsv and .tab]
- `--batch <ROWS>`: Send at most this many rows in one request [default: as many as make about 32 MiB]

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool load samples/crm-1.csv
spool load export.tsv --source crm
cat rows.csv | spool load - --source crm
```

## spool extract

Find records in documents with one of the project's extractors

Extracts records from text, on a running server. Each file is one document: the server stores its text and one of the project's extractors reads it. What the extractor finds are records like any source's rows, and the next match places them in identities.

A folder means every file under it, recursively. Dotfiles and dot-folders are skipped, and every other file must be UTF-8 text. A file you name is stored under its name. A file found in a folder is stored under its path from that folder, so naming `documents` stores documents/dev/a.txt as `dev/a.txt`.

With no path, the extractor reads every stored document it hasn't read.

Documents are read in batches, and each batch is kept when it ends. If the command stops or fails, earlier batches are kept, and running it again picks up the rest. A batch the command stops waiting for still finishes on the server. Batches are sized to a fraction of the server's user-code limit (`--task-timeout` on `spool dev` or `spool serve`), so long extractions don't need a longer limit.

An extractor's first run may download its dependencies, such as a model. On a terminal, a spinner shows the extractor's output while the first batch starts, then a progress bar counts documents. On standard error the command reports a slow start, batch totals when there are several, and the extractor's own output when its batch ends.

```text
spool extract [OPTIONS] [PATH]...
```

Arguments:

- `[PATH]...`: Files of UTF-8 text, or folders of them

Options:

- `--source <NAME>`: The source the documents belong to

  The default is the project's only source, or the one the files are named after, as notes-1.txt is after `notes`.
- `--extractor <NAME>`: The extractor [default: the project's only one]
- `--again`: Read every document of the source again, not only the new ones

  Stopped, the command starts over when it is run again.

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool extract samples/notes-1.txt
spool extract documents/ --source notes
spool extract --again
```

## spool match

Match new records and place them in identities

Matches the records no match has examined yet, on a running server. The rules judge pairs, and each new record joins the identity of the records it matches or starts a new one. Existing identities keep their IDs and their members.

Each entity type the project declares is matched in its own run, one after another, with a report for each. A failed run doesn't stop the rest, but the command then fails. `--type` matches one type.

`spool show runs <run>` shows a run's full report, and `spool show records` shows where each record is now.

With `--type`, the JSON output is the run the server returned. Without it, the output is `runs`, with each type's `entity_type` and `run`.

```text
spool match [OPTIONS]
```

Options:

- `--type <NAME>`: Only this entity type [default: every one the project declares]
- `--rematch`: Examine every record again, not only the new ones

  Records that have an identity keep it, and the run reports where the rules disagree with the identities.
- `--strategy <NAME>`: Who judges: `rules`, or one of the project's strategies for the type. Default `rules`.

  A strategy is for one entity type, which `--type` names when the project declares more than one.

It takes the [output options](#output-options) and the [server options](#server-options).

## spool recompute

Show what the current rules would change in the identities

Shows what the identities would be if every record were matched again, all at once, by the rules as they are now, against the identities there are. It changes nothing. Identities keep their members when rules change, so this is how a better rule reaches records that are already placed.

What people decided counts for more than the rules: a `must_link` or a `cannot_link` holds, records a person or an agent put together stay together, and records a reviewer dismissed from review stay without an identity. Records whose source took them back are left out.

An identity keeps its ID with the group that gets most of its records. Where several identities have their most in one group, the one with the most records there keeps its ID and the others are merged into it, so that their IDs stand for it. A group the rules join but something in it says differ waits for review without an identity, as records do after a match.

The summary comes first, then the largest changes. It ends with the command that applies it, which names a plan: a hash of where each record is and would go. Applying works the result out again and refuses if it is not that plan, so what is applied is what was shown.

```text
spool recompute [OPTIONS]
```

Options:

- `--type <NAME>`: One entity type [default: every type]
- `--identity <ID>`: Show the change that holds an identity, record by record
- `--detail`: List every change, not only the largest
- `--limit <LIMIT>`: How many changes to list [default: 10, or 1000 with --detail]
- `--offset <N>`: Pass over this many of the largest changes first
- `--apply <PLAN>`: Make the identities what the preview with this plan showed

  The change is a changeset in the log, by the engine, from runs started in your name.
- `--reason <TEXT>`: Why, kept with the changeset

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool recompute --detail
spool recompute --apply <plan> --reason "stricter name rule"
```

## spool show identities

List identities, or show one with its members and history

The list shows each identity's record count, its number of distinct names (labels, ignoring case), and the share of its record pairs that no link joins directly, which are together only through a chain. Many names and mostly unlinked pairs usually means different things were joined. `spool explain <identity>` shows which rule did it.

A single identity is shown with its members, their constraints and its history.

```text
spool show identities [OPTIONS] [IDENTITY]
```

Arguments:

- `[IDENTITY]`: An identity's ID, to show it

Options:

- `--type <NAME>`: Only this entity type
- `--sort <SORT>`: Sort by this column. One of `records`, `names`, `sources`, `label`, `entity_type`, `created`, `id`.

  `records` is how many records each has, and `names` how many different labels.
- `--order <ORDER>`: The order of the sort [default: asc]. One of `asc`, `desc`.
- `--after <ID>`: Continue the list after this ID, in its order
- `--limit <LIMIT>`: List at most this many

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool show identities --sort records --order desc
spool show identities --type company --limit 10
```

## spool explain

Say why two records share an identity, or what holds one together

With two records, it says why they share an identity or don't. You get where each one is and what placed it there, what each run that compared them concluded, the constraints and review items that name them, and what the current rules say about the pair. When they share an identity, it also shows the chain of links between them, with the rule and values behind each link, the rules every chain passes through, and the fewest links whose removal would separate them.

With one identity, it shows how much of it is held together only through chains, the pieces it would split into without each rule's links, and its weakest links: the fewest links whose removal would split it, with the two sides each would leave. That's where a wrong merge came in. Name an identity by its ID or by any of its records.

Name a record by its ID or as `<source>:<key>`, which means the latest version of that row. Name a record found in a document the way lists show it, `<source>:<document>[<start>-<end>`].

```text
spool explain [OPTIONS] <RECORD> [RECORD]
```

Arguments:

- `<RECORD>`: A record; alone, an identity, by its ID or by any of its records
- `[RECORD]`: A second record, to say why the two share an identity or do not

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool explain crm:c-1 crm:c-2
spool explain crm:c-1
```

## spool retract

Retract rows a source no longer holds

Retracts rows from a source, on a running server. Rows are named by their key, the column the source's file declares as `key`.

Every version of each row stays in the store, and leaves its identity in a changeset recorded under the caller. The identity keeps its ID and its other members. No run looks at the records again, and they can't be placed, until the source sends the row again: loading the same key, changed or not, restores every version.

Keys the source doesn't hold change nothing, so retracting is idempotent.

```text
spool retract [OPTIONS] --source <NAME> --type <NAME> [KEYS]...
```

Arguments:

- `[KEYS]...`: The keys of the rows to take back

Options:

- `--source <NAME>`: The source that held the rows
- `--type <NAME>`: Their entity type
- `--keys <FILE>`: A file of keys, one per line; `-` reads standard input
- `--reason <TEXT>`: Why, for the changeset that detaches the records

It takes the [output options](#output-options) and the [server options](#server-options).

Examples:

{/* sample: skip examples of the options, not steps that follow each other */}

```sh
spool retract --source crm --type company c-6 --reason "deleted in the CRM"
spool retract --source crm --type company --keys gone.txt
```

## spool reset

Start the development store of `spool dev` over

Deletes the development store under `<DIR>/.spool/`, with every row, document, identity, run and changeset in it, so the next `spool dev` starts empty. It lists what it will delete and keep, and asks first.

It keeps the project's files, the accounts and tokens of `spool dev` (the .auth.sqlite file beside the store), the manifest from `spool build`, and anything else under .spool/, such as an extractor's cache.

It deletes only the files DuckDB creates: `<store>.wal`, the directory `<store>.tmp` and its contents (symlinks inside it are removed, not followed), then `<store>` itself, a .duckdb file directly under `<DIR>/.spool/`. If any of these, or .spool itself, is a symlink or an unexpected file type, it deletes nothing.

It refuses while a `spool dev` has the store open: stop that one with Ctrl-C first. It only resets stores under `<DIR>/.spool/`, never one that `spool serve` runs on.

```text
spool reset [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project directory [default: the current directory]

Options:

- `--store <PATH>`: The development store, if `spool dev` was given one with `--store` [default: `<DIR>/.spool/dev.duckdb`]

  It must be directly under `<DIR>/.spool/`.
- `--yes`: Remove it without asking, which is needed where nobody can answer, as in a script

It takes the [output options](#output-options).

## spool update

Update Spool itself and refresh the project's coding-agent skills

Checks for the latest stable GitHub release and updates an installation made with install.sh. The installer verifies the archive and checks that the new binary starts before switching the command to it.

The installed binary then refreshes the project's skills, keeping edits. It does this even when Spool is already current. Outside a project, you can give its directory or run this command to update just Spool.

```text
spool update [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project to refresh [default: the current directory if it is a project]

## spool update-skills

Update the skills and AGENTS.md that tell coding agents how to use Spool

Rewrites the coding-agent files `spool init` creates, as this version of spool ships them: a skill per task in .agents/skills/ (read by Codex and Cursor), a symlink to each from .claude/skills/ (read by Claude Code), Spool's section of AGENTS.md, and a CLAUDE.md that imports AGENTS.md if there isn't one.

Files you've edited since Spool wrote them are kept, and the command lists them. --force replaces them too. Spool's section of AGENTS.md sits between two marker lines, and the rest of the file is never touched. Skills this version no longer ships are removed, unless you edited them.

Use `spool update` to install the latest release and refresh these files together.

```text
spool update-skills [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project directory [default: the current directory]

Options:

- `--force`: Replace edited files too

It takes the [output options](#output-options).

## spool build

Check a project and compile it into a manifest

Checks the project and compiles it into .spool/manifest.json, which the server reads along with the strategy and extractor files it names. Writes a Dockerfile if the project has none.

Set SPOOL_UV and SPOOL_BUN if `uv` and `bun` aren't on your PATH.

```text
spool build [OPTIONS] [DIR]
```

Arguments:

- `[DIR]`: The project directory [default: the current directory]

Options:

- `--base-image <IMAGE>`: The image the written Dockerfile starts from
- `--install`: Start each strategy and extractor once, to fetch what it needs

  Starts each strategy and extractor once with no work, so `uv` and `bun` install its dependencies, any model it loads at startup is downloaded, and a file that can't start fails now rather than later.

It takes the [output options](#output-options).

It takes the [output options](#output-options).

## spool serve

Run the server from a manifest and a store

Runs the production server. It's the only process that opens the store.

An empty store is set up from the manifest. A store applied with a different manifest is refused: run `spool apply` on it first.

A browser at the server's address gets the studio, Spool's web UI. People sign in with a username and password, and their accounts live in a file beside the store: `spool.auth.sqlite` for `spool.duckdb`. Until an admin exists, the server prints a link on startup. Whoever opens it creates the first account and becomes the admin who adds everyone else.

For a server people rely on, use Google sign-in. Set SPOOL_GOOGLE_CLIENT_ID and SPOOL_GOOGLE_CLIENT_SECRET to an OAuth client from Google's console, and the sign-in page offers it. An admin then adds people by the email of their Google account, Gmail or Google Workspace. The server prints the redirect URI for that client on startup.

Programs authenticate with a token, which an admin creates on the studio's Tokens page or with `spool token add` on this machine. Changes are recorded under the token's name, as `agent:<name>`.

Agents that speak the Model Context Protocol, such as Claude or ChatGPT, connect at `/mcp`. They get tools to load rows and documents, match, look things up and change identities, and they authenticate with a token like any other program. Claude and ChatGPT on the web can't be given a token. They sign in with OAuth: someone with an account approves them in the studio, and what they change is recorded under that person. That needs the HTTPS address people reach the server by, in `--public-url`, unless the server listens on this machine only.

Strategies and extractors run with `uv` for `.py` files and `bun` for `.ts` files. Set SPOOL_UV and SPOOL_BUN if they aren't on your PATH. The server only runs a file that matches the one the manifest was compiled from. It passes the variables the project's .env sets, except those already set in the server's environment.

On Ctrl-C or SIGTERM the server prints `stopping` and takes no new requests. Callers waiting on a run with `wait_ms` get the run as it stands. Other requests get up to 5 seconds to finish, plus 1 second for a refused client to read why, so clients are done within 6 seconds.

It then finishes every run it was given, however long they take, and prints `stopped`. Runs are never cut off halfway. If the process is killed first, the run is marked failed the next time the store opens.

```text
spool serve [OPTIONS]
```

Options:

- `--manifest <PATH>`: The manifest to run on. Default `.spool/manifest.json`.
- `--store <PATH>`: The store's database file. Falls back to `SPOOL_STORE`.
- `--listen <ADDR>`: The address to listen on. Default `0.0.0.0:7765`.
- `--public-url <URL>`: The address people reach the server by, such as https://spool.example.com. Falls back to `SPOOL_PUBLIC_URL`.

  The default is the address it listens on when that is on this machine only. Sign-in with Google comes back to it, and an agent that signs in with OAuth is sent to it.
- `--project <DIR>`: The project directory, where the files the manifest names are found [default: the current directory]
- `--no-studio`: Do not serve the studio
- `--plain-http`: Browsers reach the server over HTTP, not HTTPS

  The session cookie may then travel over HTTP. It is the default when the server listens on this machine only.

User code options:

- `--task-timeout <SECONDS>`: How long a user-code strategy or an extractor may run. Default `600`.
- `--tasks <DIR>`: Where the task directories of user code are made

  The default is `spool-tasks` in the temporary directory.

## spool token

Make, list and revoke the tokens of callers that are not people

Makes, lists and revokes the tokens of a server, on the server's machine. A token is what a caller that is not a person presents: an agent or a pipeline. What it changes is recorded under the token's name, as `agent:<name>`. An admin does the same on the studio's Tokens page.

These work whether or not the server is running.

```text
spool token [OPTIONS] <COMMAND>
```

Options:

- `--store <PATH>`: The store's database file; the tokens are in the accounts file beside it. Falls back to `SPOOL_STORE`.

It takes the [output options](#output-options).

## spool token add

Make a token, and print it

Makes a token and prints it, and nothing else, on standard output. It is shown this once: the server keeps a hash of it. A caller sends it as `Authorization: Bearer <token>`.

```text
spool token add [OPTIONS] <NAME>
```

Arguments:

- `<NAME>`: The token's name: 1 to 64 letters, digits, `.`, `_` or `-`

Options:

- `--store <PATH>`: The store's database file; the tokens are in the accounts file beside it. Falls back to `SPOOL_STORE`.

It takes the [output options](#output-options).

## spool bench

Run a benchmark scenario

Runs a benchmark scenario. For each step it loads the files, stores and extracts the documents, retracts the rows the step removes, applies its corrections and resolves, then scores the committed state against the scenario's ground truth. Scenarios with labelled mentions are also scored on extraction, and on extraction and resolution end to end. The store is verified after every step.

Strategies and extractors run with `uv` for `.py` files and `bun` for `.ts` files. Set SPOOL_UV and SPOOL_BUN if they aren't on your PATH.

```text
spool bench [OPTIONS] <SCENARIO>
```

Arguments:

- `<SCENARIO>`: A scenario.toml, or the directory that holds one

Options:

- `--db <PATH>`: The database file to build; replaced if it exists [default: .spool/bench.duckdb in the project directory]
- `--seed <SEED>`: The seed for identity and changeset IDs. Default `0`.
- `--out <PATH>`: Write the results as JSON to this file
- `--list <N>`: Print at most this many identities per step. Default `50`.
- `--strategy <NAME>`: The strategy of every step that does not name its own [default: the scenario's, or `rules`]

  `rules`, or one of the project's user-code strategies.

User code options:

- `--task-timeout <SECONDS>`: How long a user-code strategy or an extractor may run. Default `600`.
- `--tasks <DIR>`: Where the task directories of user code are made

  The default is `spool-tasks` in the temporary directory.

It takes the [output options](#output-options).

## spool completions

Print a shell completion script

Prints the script that completes `spool`'s commands, options and their values in a shell. The release puts the ones for bash, zsh and fish where those shells find them; this prints them for another place, or another shell.

```text
spool completions [OPTIONS] <SHELL>
```

Arguments:

- `<SHELL>`: The shell. One of `bash`, `elvish`, `fish`, `powershell`, `zsh`.
