The CLI, the studio and the MCP endpoint are all clients of this API. Every path is below, with examples for the ones a pipeline calls.

## Calling it

- **Address.** `spool dev` listens on `http://127.0.0.1:7765`. Every path here is under `/v1`, except `/healthz`.
- **Auth.** `spool dev` needs none. `spool serve` needs `Authorization: Bearer <token>`, with a token from `spool token add` or the studio's Tokens page.
- **Bodies.** JSON in, JSON out, on one line. JSON needs no `content-type` header. Unknown fields are rejected.
- **Waiting.** Calls that start work return immediately with a run whose `status` is `running`. Pass `wait_ms`, in the body or the query, to wait up to that long for it to finish. `GET /v1/runs/<run>?wait_ms=5000` waits on a run started earlier.
- **Pagination.** Lists return 100 entries by default, or up to 1,000 with `limit`, plus `next` when there are more. Pass it back as `after`.
- **Sorting.** `GET /v1/documents`, `/v1/records`, `/v1/identities`, `/v1/runs` and `/v1/changesets` take `sort` and `order` (`asc` or `desc`). Sorting applies to the whole list, and pages continue in that order. `order` alone reverses the default order. Sort keys:

  | Path | `sort` |
  | --- | --- |
  | `/v1/documents` | `id`, `key`, `source`, `length`, `loaded` |
  | `/v1/records` | `id`, `source`, `key`, `label`, `entity_type`, `identity` |
  | `/v1/identities` | `id`, `label`, `entity_type`, `records`, `sources`, `created` |
  | `/v1/runs` | `run`, `kind`, `status`, `details`, `started_by`, `started` |
  | `/v1/changesets` | `seq`, `actor`, `operations`, `run`, `reason` |

  Text sorts case-insensitively, and empty values sort last either way. A sorted log has no `next`, so a full page may have more after it.
- **Errors.** `{"error": {"code": "...", "message": "..."}}` with a 4xx status. The message names what was wrong.
- **Schema.** `spool schema` prints the JSON Schema for every value on this page.

## Every path

| Method and path | What it does |
| --- | --- |
| `GET /v1/info` | The project's entity types and features, sources and extractors, counts, and the log head |
| `POST /v1/load` | [Loads rows](#load-rows) into a source |
| `POST /v1/retract` | [Retracts rows](#retract-rows) a source no longer holds |
| `GET /v1/documents`, `POST /v1/documents` | Lists or stores [documents](#documents-and-extraction) |
| `POST /v1/documents/add` | [Adds one document](#add-one-document) and returns its records' identities |
| `GET /v1/documents/{document}` | One document with its text |
| `POST /v1/extractions` | Runs an extractor over the documents it hasn't read |
| `POST /v1/match` | Starts a [match](#runs) |
| `POST /v1/recompute` | Previews the identities the current rules would produce. [Read-only](#recompute) |
| `POST /v1/recompute/apply` | Applies what a recompute showed, by its `plan` |
| `GET /v1/runs` | Lists runs |
| `GET /v1/runs/{run}` | One run and its report |
| `GET /v1/runs/{run}/candidates` | The candidate pairs of a run that waits for judgements |
| `POST /v1/runs/{run}/judgements` | Sends judgements for those pairs |
| `POST /v1/runs/{run}/reconcile` | Turns a run's judgements into a changeset |
| `POST /v1/runs/{run}/cancel` | Cancels a run waiting for judgements, or stops a running extraction and discards its results |
| `GET /v1/records` | Filter by `entity_type`, `source`, `key`, `document`, `identity`, `q` (search) or `unassigned`. `latest=true` omits replaced versions, here and for documents |
| `POST /v1/records` | [Stores one row and returns its identity](#add-one-record) |
| `GET /v1/records/{record}` | One record |
| `POST /v1/records/identities` | The identity of each of many records |
| `GET /v1/attributes` | A profile per entity type and source: current records, and per attribute the fill count, distinct values, top three values and derived features. Filter by `entity_type` or `source` |
| `GET /v1/identities` | Filter by `entity_type`, `q` (search) or `ids`. Each entry has `members`, `names`, `linked_pairs` (member pairs matched directly) and `unlinked_pairs` (member pairs joined only through a chain). See [`spool show identities`](/docs/cli#spool-show). `sort=names` orders by name count |
| `GET /v1/identities/{identity}` | One identity and its records. A merged-away ID returns the identity that absorbed it |
| `GET /v1/identities/{identity}/at?seq=N` | [An identity snapshot](#identity-snapshots) after changeset `N` |
| `GET /v1/identities/{identity}/history` | Every changeset that touched it |
| `GET /v1/identities/{identity}/explain` | What holds it together: direct vs. chained pairs, the pieces it would split into without each rule, and its weakest links with the sides each would leave |
| `POST /v1/identities/{identity}/split` | Splits an identity |
| `GET /v1/explain?a=&b=` | Why two records share an identity or don't. Pass a record ID, a `source:key`, or a mention's name as lists show it |
| `GET /v1/changesets`, `POST /v1/changesets` | Reads the log, commits a [changeset](#changesets) |
| `POST /v1/changesets/{seq}/undo` | Undoes one changeset with a new one |
| `POST /v1/ids` | Mints identity IDs for `create_identity` |
| `GET /v1/constraints` | The `must_link` and `cannot_link` constraints in force, by `record` or `identity` |
| `GET /v1/review`, `GET /v1/review/{item}` | Review items, filtered by `status`, `entity_type` or `record`. All items, or a page with `limit` and `after` |
| `GET /v1/review/{item}/case` | One item with everything needed to decide it |
| `POST /v1/review/{item}/dismiss` | Closes an item without changing anything |
| `GET /v1/drafts`, `GET /v1/drafts/{draft}` | Drafts |
| `POST /v1/drafts/{draft}/approve`, `.../reject` | Commits a draft, or closes it |
| `GET /v1/people`, `POST /v1/people`, `POST /v1/people/{person}` | People's accounts. Admins only |
| `GET /v1/tokens`, `POST /v1/tokens`, `POST /v1/tokens/{token}/revoke` | Tokens. Admins only |
| `GET /healthz` | `{"status":"ok"}`, with no sign-in |

With `q`, identities are ranked by matches in their label, then aliases (other labels from their members), then other record values. Exact text ranks before prefixes and other partial matches within each name tier. An explicit sort controls the order when supplied. Each result's `match.kind` is `label`, `alias` or `record`. Label and alias matches include the matched `value`. Alias and record matches include the matching `record` ID. Record matches include `field` when a single payload field holds every search word.

Browser sign-in is under `/auth`, and the MCP endpoint is `/mcp` ([MCP](/docs/mcp)).

## Add one record

Send the source, entity type and one row to `POST /v1/records`.

```json
{"source":"crm","entity_type":"company","row":{"id":"c-1","name":"Acorn Tools","country":"GB"}}
```

The response includes `record`, `identity`, `review`, `load_run` and `match_run`. The project’s SQL rules check the submitted record against the records of existing identities. A record that needs a decision has a null `identity` and a `review` with the item ID and candidate identities. If the record is already placed or has a review item, `match_run` is null. Pending rows from other loads can be processed with `POST /v1/match`.

Repeating the same row returns the same record. To submit changed values under an existing key, set `"replace": true`. If matching fails after loading, the row remains stored and sending it again can retry placement.

## Load rows

`POST /v1/load` takes rows as JSON objects with the source's columns:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/load -d '{"source": "crm", "entity_type": "company", "wait_ms": 5000, "rows": [{"id": "c-1", "name": "Acorn Tools", "country": "GB"}, {"id": "c-2", "name": "ACORN TOOLS", "country": "GB"}, {"id": "c-5", "name": "Halden Group", "country": "GB"}, {"id": "c-6", "name": "Halden Group", "country": "US"}]}'
```

```text title="Output"
{"run":{"run":1,"kind":"load","status":"succeeded","started_by":"user:01a1f0a3-7961-77eb-b436-a883824aafc0","entity_type":"company","strategy":null,"extractor":null,"started_at":"2026-11-18T21:50:07.715530Z","finished_at":"2026-11-18T21:50:07.726734Z","error":null,"load":{"run":1,"received":4,"inserted":4,"duplicates":0,"superseded":0,"restored":0,"returned":0,"committed":null,"possible_splits":0},"extraction":null,"resolution":null,"retraction":null}}
```

The response is the load run. `received` counts rows sent, `inserted` new records, `duplicates` rows already held, and `superseded` new versions of existing rows. Nothing is matched yet.

Send CSV as is, with the source and type in the query:

```sh
curl -s -X POST 'http://127.0.0.1:7765/v1/load?source=crm&entity_type=company&wait_ms=5000' -H 'content-type: text/csv' --data-binary @samples/crm-2.csv
```

For large loads, send an Arrow IPC stream with `content-type: application/vnd.apache.arrow.stream` and the same query. The benchmarks load five million rows this way.

A row with an undeclared column, or without its key, fails the whole call. A row with an existing key and different values becomes the next version of that row. With `"replace": false`, such a row fails the whole call instead.

## Runs

A match is a run. Start one for an entity type:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/match -d '{"entity_type": "company", "wait_ms": 5000}'
```

```text title="Output"
{"run":{"run":3,"kind":"match","status":"succeeded","started_by":"user:01a1f0a3-7961-77eb-b436-a883824aafc0","entity_type":"company","strategy":{"name":"rules","version":"0.3.0"},"extractor":null,"started_at":"2026-11-18T22:10:03.814727Z","finished_at":"2026-11-18T22:10:03.832263Z","error":null,"load":null,"extraction":null,"resolution":{"entity_type":"company","match_run":3,"reconcile_run":4,"new_records":7,"reexamined":0,"candidates":4,"judgements":{"match":3,"no_match":1,"unsure":0},"identities_created":5,"records_assigned":7,"versions_moved":0,"records_unassigned":0,"review":[],"committed":{"seq":1,"changeset":"01a1f0b5-b9b0-7443-a834-945d59293e96","content_hash":"32c29e26ae8c63c31300f3c95102c1c057f4eef72609815fd8f45d4dcc80fdd6"},"draft":null,"suggestions":null},"retraction":null}}
```

| Field | Meaning |
| --- | --- |
| `entity_type` | The type to match. Required |
| `rematch` | `true` re-examines every record against the current rules, and suggests merges without making them |
| `commit` | `false` stores the changeset as a [draft](/docs/concepts/review#drafts) to approve |
| `strategy` | `{"name": "..."}`: one of the project's strategies, or any other name for a run you judge yourself. Defaults to the rules |
| `wait_ms` | How long to wait for it to finish |

The response is the match run. The reconcile run, which turned its judgements into a changeset, comes next:

## Recompute

`POST /v1/recompute` rematches every record from scratch with the current rules and returns what would change, without changing or recording anything. [Matching](/docs/concepts/matching#recompute) shows the output.

| Field | Meaning |
| --- | --- |
| `entity_type` | One type. Defaults to every type |
| `identity` | Return the change containing this identity, record by record, in `detail` |
| `limit`, `offset` | Which changes to list, largest first. Default 10, maximum 1,000 |

The response has a `plan` and, per type, a `summary`, the human `decisions` that shaped the result, `changes_total` and the requested `changes`. To apply, call `POST /v1/recompute/apply` with `{"plan": "...", "reason": "..."}` and the same `entity_type`. If the result no longer matches the plan, it returns `409` with code `conflict` and changes nothing. Otherwise it returns each type's runs, `summary`, `committed` changeset and any `review` items.

### A run you judge yourself

A run with a strategy name the project doesn't define waits for you to judge it. That's how a matcher in any language, running anywhere, plugs in: Spool finds the candidate pairs, you judge them, and Spool places records with the same four rules it uses for its own judgements.

```sh
curl -s -X POST http://127.0.0.1:7765/v1/load -d '{"source": "crm", "entity_type": "company", "wait_ms": 5000, "rows": [{"id": "c-10", "name": "Acorn Tooling", "country": "GB"}]}'
```

```sh
curl -s -X POST http://127.0.0.1:7765/v1/match -d '{"entity_type": "company", "strategy": {"name": "by-hand"}, "wait_ms": 5000}'
```

```text title="Output"
{"run":{"run":6,"kind":"match","status":"open","started_by":"user:01a1f0a3-7961-77eb-b436-a883824aafc0","entity_type":"company","strategy":{"name":"by-hand","version":null},"extractor":null,"started_at":"2026-11-18T21:50:07.836922Z","finished_at":null,"error":null,"load":null,"extraction":null,"resolution":null,"retraction":null}}
```

```sh
RUN=$(spool show runs --kind match --limit 1 | awk 'NR==2 {print $1}')
curl -s -H 'accept: application/json' http://127.0.0.1:7765/v1/runs/$RUN/candidates
```

```text title="Output"
{"candidates":[{"left_country":"GB","left_id":"34c3d52d-e53b-1559-7404-1892fb1fd4e3","left_name":"Acorn Tool","left_name_key":"acorn tool","right_country":"GB","right_id":"875986b9-a764-1450-33d1-2d4612fb4daa","right_name":"Acorn Tooling","right_name_key":"acorn tooling"},{"left_country":"GB","left_id":"875986b9-a764-1450-33d1-2d4612fb4daa","left_name":"Acorn Tooling","left_name_key":"acorn tooling","right_country":"GB","right_id":"a780fcfe-cb2f-21dd-25ea-11db898fd6a2","right_name":"ACORN TOOLS","right_name_key":"acorn tools"},{"left_country":"GB","left_id":"875986b9-a764-1450-33d1-2d4612fb4daa","left_name":"Acorn Tooling","left_name_key":"acorn tooling","right_country":"GB","right_id":"ab8e9d59-0aaa-96b9-ddb7-db0bff7a9356","right_name":"Acorn Tools","right_name_key":"acorn tools"}]}
```

Each candidate is a pair of records with their features. Without the `accept` header you get an Arrow IPC stream, which suits matchers working through many pairs. Judge them and reconcile:

```sh
LEFT=$(spool show records crm:c-10 | awk '/^record/ {print $2}')
RIGHT=$(spool show records crm:c-1 | awk '/^record/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/runs/$RUN/judgements -d '{"judgements": [{"left_id": "'$LEFT'", "right_id": "'$RIGHT'", "verdict": "match", "score": 0.97}]}'
```

```sh
curl -s -X POST http://127.0.0.1:7765/v1/runs/$RUN/reconcile -d '{}'
```

`verdict` is `match`, `no_match` or `unsure`. Pairs you don't judge stay undecided. `score` and `detail` are stored with the judgement and shown by `spool explain`.

## Add one document

Send a declared source and one text document to `POST /v1/documents/add`. Include `extractor` if the project has more than one.

```json
{"source":"notes","document":{"key":"notes-1.txt","text":"Acorn Tools Ltd renewed their account."}}
```

The response contains `document`, the stored document ID, and `records`, one entry per mention in text order. Each entry contains the `record` ID, `entity_type`, `start` and exclusive `end` in Unicode code points, and the `identity` ID or a `review` item. A record left for review has a null `identity`. Several records can share an identity, and a successful extraction with no mentions returns an empty `records` array.

Only the submitted document is extracted and its records matched. An identical retry can reuse the extraction and placements. Different text under the same source and key creates a new document version. If extraction or matching fails, the document stays stored and sending it again can resume the work.

## Documents and extraction

A document is text, stored as it arrived. Send one as is, with its source and key in the query:

```sh
curl -s -X POST 'http://127.0.0.1:7765/v1/documents?source=notes&key=notes-1.txt&wait_ms=5000' -H 'content-type: text/plain' --data-binary @samples/notes-1.txt
```

Send several as JSON:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/documents -d '{"source": "notes", "wait_ms": 5000, "documents": [{"key": "notes-1.txt", "text": "Call with Dana Reyes on 12 November. She has moved to Acorn Tools Ltd and runs purchasing there."}]}'
```

`POST /v1/extractions` runs an extractor over every document it hasn't read:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/extractions -d '{"extractor": "companies", "wait_ms": 60000}'
```

```text title="Output"
{"run":{"run":11,"kind":"extract","status":"succeeded","started_by":"user:01a1f0a3-7961-77eb-b436-a883824aafc0","entity_type":null,"strategy":null,"extractor":{"name":"companies","version":"eacb9397cacc366a1cd065d8f328039484a5e5d4fbf49b8ca1f2a3cbd34f8c92"},"started_at":"2026-11-18T21:55:21.478610Z","finished_at":"2026-11-18T21:55:22.855886Z","error":null,"load":null,"extraction":{"run":11,"documents":1,"mentions":1,"inserted":1,"duplicates":0,"superseded":0,"load_run":12,"left":0,"failed":[],"taken_back":0,"retract_runs":[],"stderr":[]},"resolution":null,"retraction":null}}
```

| Field | Meaning |
| --- | --- |
| `extractor` | The extractor to run. Optional when the project has one |
| `source` | Only the documents of this source |
| `again` | `true` rereads every document |
| `limit` | Read at most this many documents. The run's `extraction.left` says how many remain |
| `since` | Skip documents this extractor read, or failed on, in this run or later. Batched reads pass the first batch's run here |
| `wait_ms` | How long to wait for it to finish |

What the extractor finds are records, which the next match places. `failed` lists documents it couldn't read, with the reason, and the next extraction retries them. `taken_back` counts mentions no extractor finds any more, retracted by `retract_runs`. `stderr` holds the extractor's last 100 lines of standard error. [Extraction](/docs/concepts/extraction) shows extractors in both languages.

## Identity snapshots

`GET /v1/identities/{identity}/at?seq=5` reads the identity immediately after changeset `5`. It returns the same fields as the live identity read plus `as_of_seq`.

`id` and `created` describe the requested identity. `current` is the active identity it stood for at that sequence. The label and members are those of `current` at that point. Each member's `since` is the changeset that placed it there. Later merges, splits, reassignments, retractions, and undos leave earlier snapshots intact. Earlier record versions appear while they belonged to the identity.

The label is computed from the historical members using the latest saved entity declaration at the changeset's commit time. Project configuration changes alone do not create a changeset.

Sequence `0` is the empty store. The server returns `404 not_found` for an unknown identity or one created after the requested sequence, and `400 invalid` for a sequence beyond the store head or a negative sequence.

## Changesets

Every change to an identity is a changeset: one or more operations committed atomically, with an author and a reason. Matches write them, and so can any caller:

```sh
A=$(spool show records crm:c-5 | awk '/^record/ {print $2}')
B=$(spool show records crm:c-2 | awk '/^record/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/changesets -d '{"reason": "Halden Group is not Acorn Tools", "ops": [{"op": "constrain", "kind": "cannot_link", "a": "'$A'", "b": "'$B'"}]}'
```

```text title="Output"
{"seq":4,"changeset":"01a1f0a4-ca2f-7368-b562-6231f33d6cab","content_hash":"6667f62333564c8f9cb31ccb0a4c421561e9f8fd8e576f13ed45209d87800777"}
```

`seq` is its position in the log.

| Operation | Fields | What it does |
| --- | --- | --- |
| `create_identity` | `identity`, `entity_type` | Creates an identity with an ID from `POST /v1/ids` |
| `assign` | `record`, `from`, `to` | Moves a record. `from` is its current identity or `null`, and `to` is the target or `null` |
| `merge` | `from`, `into` | Moves every record of `from` into `into`. Lookups of `from` then return `into` |
| `reinstate` | `identity` | Makes a merged identity current again. Used by undo |
| `constrain` | `kind`, `a`, `b` | Adds a `must_link` or `cannot_link` between two records, which every later change must respect |
| `unconstrain` | `kind`, `a`, `b` | Removes one |

The body may include `base`, the log position you last read. Each operation states what it expects, such as an `assign`'s `from`. If any expectation no longer holds, the whole changeset is rejected and the response names the failing operation. The same happens if it would put two `cannot_link` records in one identity, or separate two `must_link` records.

Placing the latest version of a row moves its earlier versions too. The server adds those moves to the changeset, so the log can show more operations than you sent. Match runs count them in `versions_moved`.

`GET /v1/changesets?after=<seq>` reads the log. [Using the IDs](/docs/using-the-ids#follow-the-log) shows a consumer following it.

Three calls build the changeset for you:

- `POST /v1/identities/{identity}/split` with `{"records": [...], "reason": "..."}` creates an identity, moves the named records into it, and adds a `cannot_link` between the sides unless `keep_apart` is `false`.
- `POST /v1/changesets/{seq}/undo` with `{"reason": "..."}` commits the reversing changeset. With `"commit": false` it returns that changeset without committing.
- `POST /v1/drafts/{draft}/approve` commits a draft.

[Identities](/docs/concepts/identities) walks through each.

## Versioning

`v1` is the current version. Until 1.0, a release can change it, and the release notes say how.
