The server speaks the [Model Context Protocol](https://modelcontextprotocol.io) at `/mcp`, in the same process as the HTTP API and the studio. Agents connected to it can load rows and documents, run extractors, match, look things up and change identities.

- **Tools use the same store as the HTTP API.** Most return the corresponding HTTP response.
- **The server decides who the caller is.** Under `spool dev`, that's the `dev` account. Under `spool serve`, it's the agent's token, recorded as `agent:<name>`, or the person who approved an agent that signed in with OAuth. No tool lets the caller name a different author.
- **Changes carry a reason.** Tools that change identities or retract rows require a `reason`, which the log stores with the change. Loads, extractions and matches don't: the run records who started it.
- **It's stateless.** The transport is Streamable HTTP without sessions, and every response is one JSON message.

Each block below is the `params` of a `tools/call` request, exactly as an agent sends it.

## Connect a client

Against `spool dev`, which needs no token:

{/* sample: skip the two clients are not installed where the samples run */}

```sh
claude mcp add --transport http spool http://127.0.0.1:7765/mcp
codex mcp add spool --url http://127.0.0.1:7765/mcp
```

Against `spool serve`, create a token per agent, named after it, so the log shows which agent made each change. On the server's machine, `spool token add claude --store spool.duckdb` prints the token once. Then, with it in `SPOOL_TOKEN`:

{/* sample: skip the two clients are not installed where the samples run */}

```sh
claude mcp add --transport http spool https://spool.example.com/mcp --header "Authorization: Bearer $SPOOL_TOKEN"
codex mcp add spool --url https://spool.example.com/mcp --bearer-token-env-var SPOOL_TOKEN
```

Claude Desktop connects through `mcp-remote`, a local proxy that adds the header. In `claude_desktop_config.json`:

```json title="claude_desktop_config.json"
{
  "mcpServers": {
    "spool": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://spool.example.com/mcp", "--header", "Authorization:${SPOOL_AUTH}"],
      "env": { "SPOOL_AUTH": "Bearer <token>" }
    }
  }
}
```

The MCP SDKs, the Claude API's MCP connector and the OpenAI Responses API's `mcp` tool also take the address and token.

### Claude and ChatGPT on the web

These can't be given a token. They sign in with OAuth: the server is the authorization server for its own `/mcp`, someone with an account approves the agent in the studio, and changes are recorded as `user:<id>`.

They call from Anthropic's and OpenAI's networks, so the server needs public HTTPS on port 443, given with `--public-url` or `SPOOL_PUBLIC_URL`. [Running the image](/docs/deploying#running-the-image) is where that address is set. A server listening on `0.0.0.0` without one, or over plain HTTP, has no OAuth and prints `oauth off` at startup.

- **Claude.** Customize, Connectors, Add custom connector. Enter `https://spool.example.com/mcp`. Under OAuth client, choose **Register automatically**. Spool registers clients itself and doesn't take Claude's published identity, which is the default. On a Team or Enterprise plan, an Owner adds it under Organization settings, Connectors.
- **ChatGPT.** Plugins, the plus button, Add custom MCP server. Enter the same address, choose OAuth, and create it as a plugin.

The studio opens. Sign in, check the host the approval returns to (`claude.ai` or `chatgpt.com`), and approve. The approval lasts as long as that sign-in, without the 12-hour cap. Turning the account off, replacing the password, or changing the account's Google email ends it, and turning the account back on doesn't bring it back. An admin sees every approval under Assistants on the Tokens page and can revoke one.

| What | How long |
| --- | --- |
| The code the browser brings back | 2 minutes, once |
| An access token | 1 hour, at `/mcp` only |
| A refresh token | 30 days, once. Each refresh gives the next, and using one twice ends the approval |

One scope, `spool`: read and change data, not manage people or tokens. An organisation whose Owner sees **Request headers** in Claude can instead send `Authorization: Bearer <token>`.

## Before you start

The examples pick up where [Getting started](/docs/getting-started) leaves off, with both CSV files loaded and matched. If that server's still running, use it. Otherwise:

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

{/* sample: background */}

```sh
spool dev
```

Leave it running. In a second terminal, in `companies`:

```sh
spool load samples/crm-1.csv
spool match
spool load samples/crm-2.csv
spool match
```

One more row gives the agent something to review, a Halden Group with no country:

```csv title="halden.csv"
id,name
c-13,Halden Group
```

```sh
spool load halden.csv --source crm
spool match
```

## Tools that look things up

Each is marked read-only for the client.

| Tool | What it answers | The same as |
| --- | --- | --- |
| `describe_store` | Entity types and features, sources and columns, extractors, counts, and the log head | `GET /v1/info` |
| `search_identities` | Identities by name or record values, by type or by ID | `GET /v1/identities` |
| `get_identity` | One identity and its records | `GET /v1/identities/{id}` |
| `get_identity_history` | Every change that touched an identity | `GET /v1/identities/{id}/history` |
| `get_identity_at` | An identity's label, members and merge redirect immediately after a changeset | `GET /v1/identities/{id}/at?seq=N` |
| `search_records` | Records by words, source, key or identity, with their values | `GET /v1/records` |
| `get_record` | One record | `GET /v1/records/{id}` |
| `explain_pair` | Why two records share an identity or don't. Name records by ID, `source:key`, or a mention's name as lists show it | `GET /v1/explain` |
| `list_review_items` | Cases waiting for a decision, open ones by default | `GET /v1/review` |
| `get_review_case` | One review item with everything needed to decide it | `GET /v1/review/{id}/case` |
| `list_constraints` | The `must_link` and `cannot_link` constraints in force | `GET /v1/constraints` |
| `list_changesets` | Changeset summaries and operation counts after a log position | Summarizes `GET /v1/changesets` |
| `list_changeset_ops` | A page of operations from one committed changeset | |
| `get_run` | One run: its status and report | `GET /v1/runs/{run}` |
| `mint_identity_ids` | New identity IDs for a `create_identity` operation | `POST /v1/ids` |


```json title="MCP tool call"
{ "name": "get_review_case", "arguments": { "item": 1 } }
```

The case bundles the item, its records and values, the identities they matched with their members, and the judgements between them, so the agent gets everything in one call.

The changeset log lists summaries in ascending `seq` order. Each summary includes the changeset's ID, base, author, reason, run, content hash and `operation_count`. For run-generated changesets, `started_by` identifies who requested the run. A summary's optional `left_out` names metadata fields omitted because of their size. `head` is the latest committed position. To continue, pass `next` as `after` until `next` is null.

```json title="MCP tool call"
{ "name": "list_changesets", "arguments": { "after": 1, "limit": 1 } }
```

Use the summary's `seq` to read the operations in commit order. Omit `offset` for the first page, then pass each response's `next` as `offset` until it is null.

```json title="MCP tool call"
{ "name": "list_changeset_ops", "arguments": { "seq": 2, "limit": 20 } }
```

```json title="MCP tool call"
{ "name": "mint_identity_ids", "arguments": { "count": 1 } }
```

```text title="Output"
{"identities":["01a1efaa-1ba3-7566-8623-0e9b224b63c9"],"changesets":[]}
```

## Tools that change something

Each is marked as a change, so the client can ask the user first.

| Tool | What it does | The same as |
| --- | --- | --- |
| `commit_changeset` | Merges identities, moves or places records, creates identities, adds and removes constraints | `POST /v1/changesets` |
| `split_identity` | Splits one identity in two and keeps the sides apart | `POST /v1/identities/{id}/split` |
| `undo_changeset` | Reverses a committed changeset, or previews the reversal | `POST /v1/changesets/{seq}/undo` |
| `dismiss_review_item` | Closes a review item without placing its records | `POST /v1/review/{id}/dismiss` |

Five more load, extract, match and retract. They're [further down](#tools-that-load-extract-and-match).

`commit_changeset` takes [the HTTP API's operations](/docs/api#changesets). Here the agent records that the two Halden Groups are different companies, so no later rule or reviewer merges them:

```json title="MCP tool call"
{ "name": "commit_changeset", "arguments": {
  "reason": "registered in different countries, with different company numbers",
  "ops": [ { "op": "constrain", "kind": "cannot_link", "a": "$GB", "b": "$US" } ] } }
```

```text title="Output"
{"seq":3,"changeset":"01a1efaa-1ba5-7158-b323-9365dc19b5e7","content_hash":"9b1ab005c425ddd81c5b1ee95101788266b244020147781da5cd9d0ce4c8f5e4"}
```

```json title="MCP tool call"
{ "name": "list_constraints", "arguments": { "record": "$GB" } }
```

`split_identity` names the records that leave. They get a new identity, and the original keeps its ID:

```json title="MCP tool call"
{ "name": "split_identity", "arguments": { "identity": "$ACORN", "records": ["$TOOL"],
  "reason": "Acorn Tool is a hardware shop in Leeds, not Acorn Tools" } }
```

`undo_changeset` takes a log position. With `"commit": false`, it returns the reversing changeset without committing:

```json title="MCP tool call"
{ "name": "undo_changeset", "arguments": { "seq": 4, "commit": false, "reason": "checking what an undo would do" } }
```

```text title="Output"
{"changeset":{"id":"01a1f0a2-34c3-73a7-844e-eb8ac6aab102","base":4,"actor":"user:01a1f0a2-3336-72d8-8d23-74f15ece6783","reason":"checking what an undo would do","run":null,"ops":[{"op":"unconstrain","kind":"cannot_link","a":"34c3d52d-e53b-1559-7404-1892fb1fd4e3","b":"31075f20-6900-838b-f5af-f8c6576744a4"},{"op":"assign","record":"34c3d52d-e53b-1559-7404-1892fb1fd4e3","from":"01a1f0a2-34bb-729b-bdb0-e47ff384bcb8","to":"01a1efc6-41cd-775d-8758-e7300637659a"}]},"committed":null}
```

```json title="MCP tool call"
{ "name": "undo_changeset", "arguments": { "seq": 4, "reason": "the shop is a branch of Acorn Tools after all" } }
```

`dismiss_review_item` closes an item the agent can't decide, with a reason:

```json title="MCP tool call"
{ "name": "dismiss_review_item", "arguments": { "item": 1, "reason": "the row has no country, so it cannot be told which Halden Group it is" } }
```

## Tools that load, extract and match

```json title="MCP tool call"
{ "name": "load_rows", "arguments": { "source": "crm", "entity_type": "company",
  "rows": [ { "id": "c-20", "name": "Kestrel Analytics Inc", "country": "US" } ] } }
```

```json title="MCP tool call"
{ "name": "run_match", "arguments": { "entity_type": "company" } }
```

```json title="MCP tool call"
{ "name": "get_run", "arguments": { "run": 11 } }
```

```json title="MCP tool call"
{ "name": "load_documents", "arguments": { "source": "notes",
  "documents": [ { "key": "notes-2.txt", "text": "Dana called again. Acorn Tools Ltd are moving their account next quarter." } ] } }
```

```json title="MCP tool call"
{ "name": "run_extraction", "arguments": { "extractor": "companies" } }
```

| Tool | What it does | The same as |
| --- | --- | --- |
| `add_record` | Stores one row and returns its record and identity or review item | `POST /v1/records` |
| `add_document` | Stores and extracts one text document and returns the identity or review item for each record | `POST /v1/documents/add` |
| `load_rows` | Loads rows, as objects, into a source | `POST /v1/load` |
| `load_documents` | Stores text as documents of a source | `POST /v1/documents` |
| `run_extraction` | Runs an extractor over documents it hasn't read | `POST /v1/extractions` |
| `run_match` | Places records no match has examined, and commits the result | `POST /v1/match` |
| `retract_rows` | Retracts rows by key: they leave their identities and stay in the store | `POST /v1/retract` |

Call `add_record` with `source`, `entity_type` and a single `row` object. The server returns the `record` and `identity` IDs. If the record needs review, `identity` is null and `review` gives the item ID and candidate identities. Set `replace` to true to change a row under an existing key.

Call `add_document` with `source` and a `document` object containing `key`, `text` and optionally `uri`. Pass `extractor` if the project declares more than one. The response contains the document ID and each record's ID, text span, and identity or review item. [Add one document](/docs/api#add-one-document)

The bulk load, extraction, match and retraction tools return a run. A run still going after 30 seconds comes back as `running`, and `get_run` with `wait_ms` waits up to 60 seconds more.

Differences from the HTTP API:

- **`load_rows` doesn't replace rows by default.** A row with a known key and different values fails the whole call unless you pass `"replace": true`. `POST /v1/load` replaces it.
- **`add_record` and `load_rows` treat empty values as missing**, like `spool load`. JSON rows sent over HTTP store `""` as text.
- **`load_documents` rejects undeclared sources.** `POST /v1/documents` stores the document anyway.
- **`run_extraction` needs no `extractor`** when the project has only one.
- **`run_match` always commits.** It takes `rematch` and `strategy` (`rules` or one of the project's strategies), but not `commit`.
- **`retract_rows` requires a `reason`.**

## Reserved for people

- **Approving or rejecting drafts.** Drafts exist so a person decides, in the studio or over `/v1`.
- **Adding people and creating tokens.**
- **Editing project files.** Rules, features and sources live in Git. An agent edits them like any contributor to the repository.

Agents always write under their own name with a reason. They read documents through the records extracted from them. A match an agent starts commits, like `spool match`. To hold one for approval, start it over HTTP with `"commit": false`, as [Review](/docs/concepts/review#drafts) shows.

## Protocol details

- Requests are capped at 4 MiB.
- Lists return 20 entries unless you pass `limit`.
- Responses are capped at 256 KiB. An oversized lookup returns an error asking for less. An oversized change still commits, and the response omits its large fields, listed in `left_out`.
- Failures are readable by the model: the result has `isError` set and the API's error as text.
- Supported protocol revisions: `2024-11-05` to `2026-07-28`.
