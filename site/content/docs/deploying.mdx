---
title: Deploying
description: Run Spool for a team with spool build, spool apply and spool serve. Sign people in, give programs tokens, ship the image, and back up the store.
---

`spool dev` is for one person on one machine. `spool serve` is the server your team and your pipelines reach. Same binary, same store format. The differences: every caller is authenticated, and the server runs from a compiled manifest instead of the project's files.

## What a deployment is

- **One process** on one machine.
- **One store file**, a DuckDB database that only that process opens.
- **One accounts file** beside it, named after it (`spool.auth.sqlite` for `spool.duckdb`), holding people and tokens.
- **The project** at the version you built: the manifest, plus any strategy and extractor files.

## Build

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

```sh
spool build
```

```text title="Output"
manifest  ./.spool/manifest.json
hash      b6dff33d6c0977f4afb2497792bcaa9785e8b865994fa5c94eb9761f57a6e0a7
types     company
wrote     ./Dockerfile
wrote     ./.dockerignore
```

`spool build` checks the project and writes `.spool/manifest.json`, with every rule and declaration and a hash of the whole. It also writes a `Dockerfile` and `.dockerignore` if the project has none.

## Apply

```sh
spool apply --store spool.duckdb
```

```text title="Output"
store     spool.duckdb
manifest  b6dff33d6c0977f4afb2497792bcaa9785e8b865994fa5c94eb9761f57a6e0a7
declared  company
```

`spool apply` creates the store if needed, declares new entity types, and rebuilds features for each type whose declaration changed. Identities aren't touched. It runs with the server stopped, so a rule change is: build, stop, apply, start.

## Serve

{/* sample: background */}

```sh
spool serve --store spool.duckdb --listen 127.0.0.1:7765
```

```text title="Output"
manifest  b6dff33d6c0977f4afb2497792bcaa9785e8b865994fa5c94eb9761f57a6e0a7
accounts  spool.auth.sqlite
listening on http://127.0.0.1:7765
studio    http://127.0.0.1:7765/
mcp       http://127.0.0.1:7765/mcp
setup     http://127.0.0.1:7765/setup#8903cd40f174a29b7c4f4151e5f06e9105827d80da047fb278e18ca1cab9193c
no admin can sign in yet: open that link, at the address people reach this server by, to make the first account
```

`--listen` defaults to `0.0.0.0:7765`. Put a TLS-terminating reverse proxy in front, and pass the public address with `--public-url https://spool.example.com`.

The server refuses a store applied with a different manifest, and tells you to run `spool apply` first.

## The first account

Until an admin exists, the server prints a setup link on startup. Whoever opens it creates the first account, with a username and password, and becomes the admin who adds everyone else on the studio's People page.

Passwords get you started. For a server people rely on, use Google sign-in: set `SPOOL_GOOGLE_CLIENT_ID` and `SPOOL_GOOGLE_CLIENT_SECRET` to a "Web application" OAuth client whose redirect URI is the public URL plus `/auth/google/callback`. The server prints the exact value on the line starting with `google`. An admin then adds each person by their Google account email.

## Tokens for programs

Pipelines and agents authenticate with a token. Create one on the server's machine, or on the studio's Tokens page:

```sh
TOKEN=$(spool token add pipeline --store spool.duckdb)
```

```text title="Output"
That is the token `pipeline`, kept in spool.auth.sqlite. It is shown this once.
A caller sends it as `Authorization: Bearer <token>`, and what it changes is recorded under `agent:pipeline`.
```

The token is the only thing on standard output, so you can capture it in a variable. It's shown once, and the server stores only a hash.

```sh
spool token list --store spool.duckdb
```

```text title="Output"
TOKEN     MADE AT                   MADE BY          LAST USED
pipeline  2026-11-18T17:22:33.382Z  spool token add  never
```

Callers send it as a bearer token, and their changes are recorded as `agent:pipeline`:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/load -H "Authorization: Bearer $TOKEN" -d '{"source": "crm", "entity_type": "company", "wait_ms": 5000, "rows": [{"id": "c-1", "name": "Acorn Tools", "country": "GB"}]}'
```

Without one, the request is rejected:

```sh
curl -s http://127.0.0.1:7765/v1/info
```

```text title="Output"
{"error":{"code":"unauthorized","message":"sign in, or send a token: `Authorization: Bearer <token>`"}}
```

The CLI reads the token from `SPOOL_TOKEN` and the address from `SPOOL_URL`:

```sh
SPOOL_TOKEN=$TOKEN spool show
```

```text title="Output"
server     http://127.0.0.1:7765
api        v1, engine 0.3.0, store format 12
manifest   b6dff33d6c0977f4afb2497792bcaa9785e8b865994fa5c94eb9761f57a6e0a7
head       log position 0
documents  0

entity type `company`
  records     1, 1 without an identity
  identities  0
  review      0 items open

extractor `companies` (python, extractors/companies.py)
```

There are two roles. Admins add people and create tokens. Everyone else, and every token, can read everything and change identities.

## A container

{/* sample: skip needs Docker, and the build fetches the sample extractor's model */}

```sh
docker build -t companies .
docker run -p 7765:7765 -v spool-data:/data companies
```

The generated Dockerfile starts from `ghcr.io/alexpatow/spool:0.3.0`, builds the manifest, and runs `spool serve` with the store at `/data/spool.duckdb` on a volume. For projects with Python files, like the sample, it also copies in `uv` and runs `spool build --install`, which installs every strategy's and extractor's dependencies, including the sample model, so the server downloads nothing at runtime. To apply a changed project, stop the server and run `docker run --rm -v spool-data:/data companies apply`.

The generated `.dockerignore` keeps `.env` out of the image. Pass your code's variables at runtime, for example with `docker run --env-file .env`. Without Docker, set them in `spool serve`'s environment, or put a `.env` in the project directory named by `--project`.

The image runs as the user `spool`, uid 10001. The store is a file on the volume at `/data`, so that volume has to be writable by `spool`. That user has no login shell. The Dockerfile is the project's once `spool build` has written it, so give `spool` a shell there if you need one in the container.

## Running the image

Any host that builds a Dockerfile can run the image `spool build` writes. It needs four things, and one instance: one process opens the store.

Leave `.spool/`, `.env` and any data you load out of what the host builds. The store goes on the disk, not in the image.

- **The image** is that Dockerfile. It starts from `ghcr.io/alexpatow/spool:<version>` and runs `spool serve`.
- **The public URL.** Set `SPOOL_PUBLIC_URL` to the HTTPS address people open, such as `https://spool.example.com`. Sign-in with Google and an agent that signs in with OAuth both use the address you set. Google's redirect URI is that address followed by `/auth/google/callback`.
- **The disk.** Mount a persistent disk at `/data`. It has to outlive a new container, and it has to be writable by uid 10001 before the server starts. The store is `/data/spool.duckdb` unless `SPOOL_STORE` names another file there.
- **The start command.** The image listens on `0.0.0.0:7765`. The `CMD` at the bottom of the Dockerfile is the command. If the host chooses the port and puts it in `PORT`, set `--listen` to `0.0.0.0:$PORT`.

The server prints the setup link in its logs. Open it before anyone else does: whoever opens it is the admin. Connect Claude and ChatGPT on the web to the public URL followed by `/mcp`, as [MCP](/docs/mcp#claude-and-chatgpt-on-the-web) says.

What to know:

- **Memory.** Half a gigabyte holds rows and rules on a small store. A project whose extractor loads a model in the server, as the sample project's does, needs about 2 GB.
- **Secrets your code reads**, such as a model's API key, go in the service's environment. Without one, an extractor that needs it fails rather than calling anyone.
- **A deploy** replaces the container and has to keep the disk. The server stops while that happens, because the next process cannot open the store until this one has let go of it.
- **A changed project** builds a new manifest, and the server refuses a store applied with another until it is applied again. With the server stopped, set the start command to the `apply` command at the top of the Dockerfile, the part after the image's name. When the logs show the `manifest` line of `spool apply`, set the start command back to `serve`. That first run is reported as failed, because `apply` ends.

### Moving a store

A store made elsewhere, with `spool dev` or another server, moves as its file. The server has to run on a manifest with the same hash, which the same project files give.

1. Stop the server that has the store open. Copy `<name>.duckdb`, and `<name>.duckdb.wal` if there is one: it holds the last changes.
2. Put the files on the disk under a name the running server is not using, owned by uid 10001: `/data/moved.duckdb`, and `/data/moved.duckdb.wal` when you have one.
3. Set `SPOOL_STORE` to `/data/moved.duckdb` and start the server. Accounts live beside a store and are named after it, so the server prints a setup link for `/data/moved.auth.sqlite`. To keep the people and approvals you had, copy the accounts file to `/data/moved.auth.sqlite` first, also owned by uid 10001.

## Backing up

The store is one file and the accounts are another. Stop the server, copy both, start it again.

Everything that decides an identity is in the store: the records, every judgement, and the full log. Nothing is derived from the project at read time, so a copy of the store is a complete copy of the identities.

## Upgrading

Releases that can upgrade a store do it when the store opens, and the release notes list the formats each reads. Copy the store before starting a new version on it. The format can change before 1.0.

## Stopping

On Ctrl-C or SIGTERM the server prints `stopping`, refuses new requests, finishes in-flight requests within six seconds, completes every run it was given, and prints `stopped`. If the process is killed first, the run is marked failed when the store next opens.

## Operating it

- **Memory.** A match holds its candidate pairs in memory. In the benchmark, five million records with 76 million candidate pairs peaked at 13.4 GB.
- **One writer.** Writes run one after another, so a load that arrives during a long match waits for it.
- **Health check.** `GET /healthz` returns `{"status":"ok"}` without auth.
- **User code.** Strategies and extractors need `uv` (Python) or `bun` (TypeScript) on the server, and each run is capped by `--task-timeout`, 600 seconds by default.
