title: Matching
description: Block rules pick the pairs worth comparing, match and no_match rules judge them, and a match places new records without moving existing identities.
---

Matching answers one question about two records: are they the same thing? Spool's answer is a **judgement**: `match` or `no_match`, or `unsure` from a strategy written in code. Judgements are stored, and change nothing until a run turns them into identities.

This page covers the three kinds of rule, what a match does with their judgements, the trade-off that keeps IDs stable, and how to roll out a better rule.

## Before you start

The examples pick up where [Getting started](/docs/getting-started) leaves off, with both CSV files loaded and matched. If that server's still running, use it. Otherwise:

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

{/* sample: background */}

```sh
spool dev
```

Leave it running. In a second terminal, in `companies`:

```sh
spool load samples/crm-1.csv
spool match
spool load samples/crm-2.csv
spool match
```

## Three kinds of rule

A rule is a SQL file holding one condition over two rows of the feature table, `l` and `r`. The file name is the rule's name, and its directory sets its kind.

| Directory | What a rule there says |
| --- | --- |
| `rules/block/` | This pair is worth comparing. Pairs no block rule finds are never compared. |
| `rules/match/` | This pair is the same thing. |
| `rules/no_match/` | This pair isn't the same thing. Beats every match rule. |

The sample project has one of each:

{/* sample: existing */}

```sql title="entities/company/rules/block/name_prefix.sql"
-- A block rule says which pairs are worth comparing: here, two names that
-- begin with the same four characters. `l` and `r` are two rows of the
-- feature table.
left(l.name_key, 4) = left(r.name_key, 4)
```

{/* sample: existing */}

```sql title="entities/company/rules/match/similar_name.sql"
-- A match rule says a pair is the same thing: here, two names that are
-- close. The similarity is 1 for equal names and 0 for names with nothing
-- in common.
jaro_winkler_similarity(l.name_key, r.name_key) >= 0.92
```

{/* sample: existing */}

```sql title="entities/company/rules/no_match/different_country.sql"
-- A no_match rule says a pair is not the same thing, and wins over any
-- match rule. This one holds only when both rows have a country.
l.country <> r.country
```

`name_key` is a [feature](/docs/concepts/entity-types-and-features): the name, lowercased and trimmed.

Block rules exist because comparing every record with every other doesn't scale. Make each one an equality, so the database can find pairs with a join. An equality over an expression is fine, as here. Use one file per equality: an `OR` in a block rule compares everything with everything.

For each pair the block rules find, the judgement is:

1. `no_match` if any no_match rule holds,
2. otherwise `match` if any match rule holds,
3. otherwise no judgement at all.

## Empty values

As in SQL, comparing with a NULL feature is neither true nor false, so a rule that's only that comparison doesn't hold. `l.country <> r.country` doesn't separate two records with no country.

In rules with `AND`, `OR` or `NOT`, use `coalesce` to say what NULL means: `coalesce(l.country = r.country, false)` holds only when both have a country and they're equal, and `NOT coalesce(l.country <> r.country, false)` holds unless both have a country and they differ.

## What a match does

`spool match` starts a run. Its scope is one entity type's records that are new since the last successful run, plus any left in review. It compares new records with each other and with placed ones, never two placed records with each other.

It then turns judgements into identities by four fixed rules:

1. A new record that matches members of exactly one identity, with no `no_match` against it, joins that identity.
2. New records that match only each other form a new identity.
3. A new record that matches members of two or more identities waits without one, and a [review item](/docs/concepts/review) is raised.
4. A run never merges or splits existing identities.

Load three rows that exercise them:

```csv title="crm-3.csv"
id,name,country
c-10,Acorn Tooling,GB
c-11,The Halden Group,GB
c-12,Kestrel Analytics,GB
```

```sh
spool load crm-3.csv
spool match
```

## The cost of IDs that stay

Rule 4 is why you can store an ID elsewhere and trust it. It also makes results depend on arrival order. Two records that arrive together and match become one identity. The same two, each placed before a rule linked them, stay apart until someone merges them.

So a better rule doesn't rewrite old data by itself. Here's what it does instead.

## Rules that get better

`crm:c-11` should have joined Halden Group. Make the transform drop a leading "the":

```sql title="transforms/name_key.sql"
-- Lower case, without the space around it or a leading "the".
lambda name: regexp_replace(lower(trim(name)), '^the ', '')
```

`spool dev` recomputes the features. No identity changes, because both records are placed. To see what the better rule says about placed records, run `--rematch`, which compares every record of the type:

```sh
spool match --rematch
```

```text title="Output"
run         10, type `company`
examined    0 records without an identity and every record placed before, 15 candidate pairs
judgements  11 match, 3 no_match
placed      0 records, 0 identities created
suggested   1 merge, 0 splits: `spool show runs 10` lists them
```

The run placed and moved nothing. It reports a **suggested merge**: two identities with matches between their members. A person or agent who agrees merges them, as [Identities](/docs/concepts/identities#merge) shows. A rematch reports suggested splits the same way, when a no_match rule holds between two members of one identity.

A better matcher run over old data produces suggestions, not changes to IDs other systems have stored.

Suggestions live in the run's report, not as review items. `spool show runs <run>` lists them, and `GET /v1/runs/<run>` returns them as JSON. They aren't paginated, so a rule change that suggests thousands of merges produces a report thousands of lines long.

## Recompute

A rematch shows where the rules disagree. `spool recompute` shows what the identities would be: it matches every record from scratch with the current rules, as a fresh store would, and compares the result with the identities you have. It changes nothing.

```sh
spool recompute
```

```text title="Output"

unchanged  5 identities would keep exactly their records
merged     1 identity would take records from more than one; 1 identity merged into another, its ID standing for it
gain       1 identity would gain records
moved      1 record would change identity
pairs      11 pairs share an identity now, 12 would after, 11 of them both

1 change, the largest first

1  merge  2        01a1efc6-41cd-775d-8758-e7329447fd9a  Halden Group (1), The Halden Group (1)  Halden Group (2, keeps its ID, 1 identity merged in)
`--identity <id>` shows a change record by record

spool recompute --apply 0f0ae22918643710b875675543062faa05f144d428242c6efd7be2f9cce68d69
```

The summary comes first. **pairs** measures how far apart the two groupings are: record pairs that share an identity now, after, and in both. Then come the changes, largest first. A change groups the before and after identities that share records. Its kind is `split`, `merge`, `regroup` (several into several), `gain`, `lose` (records that would wait for review), `new` or `review` (every record would wait). Ten are listed by default. `--detail` lists all, and `--limit` and `--offset` page them, so large projects start with the biggest changes.

`--identity` shows one change record by record:

```sh
HALDEN=$(spool show records crm:c-5 | awk '/^identity/ {print $2}')
spool recompute --identity $HALDEN
```

Which identity keeps its ID follows the same rule as a split: an identity keeps its ID with the group that gets most of its records. If several identities have their most records in one group, the one with the most there keeps its ID (the older one on a tie), and the others merge into it, so systems that stored their IDs still find the entity. A group where no identity has its most records becomes a new identity.

Applying is a separate step. The preview ends with the command, and its hash is the plan, also available in the JSON:

```sh
PLAN=$(spool recompute --json | jq -r .plan)
spool recompute --apply $PLAN --reason "names without a leading the"
```

```text title="Output"
type        `company`, match run 12, reconcile run 13
changeset   at log position 4, by the engine: `spool show log` has it
identities  6 now, from 7: 0 made, 1 merged away
records     1 moved, 0 placed, 0 left an identity

applied plan 0f0ae22918643710b875675543062faa05f144d428242c6efd7be2f9cce68d69
```

Apply recomputes and refuses if the result isn't that plan, so what's applied is exactly what you saw. If rows were loaded, rules changed or identities moved in between, it says so and changes nothing. The match run stores its judgements like any run, and the changes land as one changeset authored by the engine, with the run recorded as started by whoever applied it. `POST /v1/changesets/<seq>/undo` reverses it like any other changeset.

Human decisions outrank the rules, as [Review](/docs/concepts/review#recompute-and-what-people-decided) details. A `must_link` or `cannot_link` holds, records a person or agent put together stay together, records a reviewer dismissed stay unplaced, and retracted records are left out. If the rules join a group that contains a known difference, the group waits for review, as new records do after a match. What people put together in such a group stays an identity, and only the rest waits.

Nothing recomputes automatically. A rule change alone never moves an identity.

## Other ways to judge

SQL rules are the built-in strategy. A project can also hold strategies in Python or TypeScript under `entities/<type>/strategies/`, run as child processes with `uv` or `bun`. They read candidate pairs and write judgements, including `unsure`, and the same four rules turn them into identities. [`benchmarks/resolution/people`](https://github.com/alexpatow/spool/tree/main/benchmarks/resolution/people) has a strategy that runs Splink.

A caller can also open a run, fetch candidates over the API and send its own judgements. See [the HTTP API](/docs/api#runs).

## Scope of rules

- The four placement rules are fixed.
- Recompute runs the SQL rules. Strategies written in code aren't recomputed.
- SQL rules return `match`, `no_match` or nothing. Only strategies return `unsure`.
- A rule sees two records' features, not their sources.
- Rules compare records of one entity type.
