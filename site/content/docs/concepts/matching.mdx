---
title: Matching
description: Block rules pick the pairs worth comparing, match and no-match rules judge them, and a run turns the judgements into identities without moving the ones that exist.
---

Matching answers one question about two records: are they the same thing? In Spool the answer is a **judgement**: `match`, `no_match` or `unsure`. Judgements are evidence. They are kept, and they change nothing until a run turns them into identities.

This page covers the three kinds of rule, what a run does with their verdicts, and what to do when a rule gets better. Rules read the [features](/docs/concepts/entity-types-and-features) of two records. What a run decides becomes [identities](/docs/concepts/identities), and what it will not decide goes to [review](/docs/concepts/review).

The examples continue the project from [Entity types and features](/docs/concepts/entity-types-and-features), with `spool dev` running.

## Three kinds of rule

A rule is a SQL file that holds one condition over two rows of the feature table, `l` and `r`. The file's name is the rule's name, and the directory it is in says what kind it is.

| Directory | What a rule there says |
| --- | --- |
| `rules/block/` | This pair is worth comparing. Pairs that no block rule finds are never compared. |
| `rules/match/` | This pair is the same thing. |
| `rules/no_match/` | This pair is not the same thing. It wins over every match rule. |

Block rules exist because comparing every record with every other does not scale. A block rule should be a plain equality, such as `l.domain = r.domain`, so that the database can find the pairs with a join. Write one file per equality: a block rule that says `OR` compares everything with everything.

For each pair the block rules find, the verdict is:

1. `no_match` if any no-match rule holds,
2. otherwise `match` if any match rule holds,
3. otherwise no judgement at all.

A condition that reads an empty feature is neither true nor false, as in SQL, so it does not hold. Two records without a domain are not matched by `l.domain = r.domain`.

## Add rules

Two companies with the same website domain are one company:

```sql title="entities/company/rules/block/same_domain.sql"
l.domain = r.domain
```

```sql title="entities/company/rules/match/same_domain.sql"
l.domain = r.domain
```

Two companies in different countries are different legal entities, however alike their names:

```sql title="entities/company/rules/no_match/different_country.sql"
l.country <> r.country
```

## What a run does

A match run has a scope: the records of one entity type that are new since the last run of that type that succeeded, plus any that an earlier run left for review. It compares new records with each other and with existing ones. It does not compare two records that are both already placed.

It then reconciles the judgements with the identities that exist. The policy is fixed and conservative:

1. A new record that matches members of exactly one identity, with no `no_match` against it, joins that identity.
2. New records that match only each other form a new identity.
3. A new record that matches members of two or more identities is left without an identity, and a [review item](/docs/concepts/review) is recorded.
4. Existing identities are never merged or split by a run.

The result is one [changeset](/docs/concepts/identities#the-log), committed by default. A run started with `"commit": false` stores it as a draft for someone to approve.

When nothing is new, `POST /v1/runs` answers `{"run":null}` and does nothing.

Rule 4 is the reason IDs are stable, and it makes the policy depend on the order records arrive in. Two records that arrive in one batch and match each other become one identity. The same two records, each placed in its own identity before a rule existed that matches them, stay apart until someone merges them.

## Rules that get better

`registry:X001` should have matched Acorn Tools. Make the transform drop legal forms from the end of a name:

```sql title="transforms/name_key.sql"
-- Lower case, and legal forms removed from the end.
lambda name: regexp_replace(lower(trim(name)), '( (ltd|limited|inc))+$', '')
```

`spool dev` rebuilds the features. No identity changes, because both records are already placed. To see what the better rule would say about records that are placed, start a run with `rematch`, which compares every record of the type:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/runs -H 'content-type: application/json' -d '{"entity_type": "company", "rematch": true}'
```

```sh
spool show runs 16
```

The run placed nothing and moved nothing. It reports a **suggested merge**: two identities with matches between their members. A person or an agent who agrees merges them, which [Identities](/docs/concepts/identities#merge) shows. A rematch reports suggested splits the same way, when a no-match rule holds between two members of one identity.

This is deliberate. A better matcher run over old data produces a list of suggestions, not a change to IDs that other systems have stored.

## Other ways to judge

SQL rules are the built-in strategy. A project can also hold strategies written in Python or TypeScript under `entities/<type>/strategies/`, which the server runs as child processes with `uv` or `bun`. They read candidate pairs and write judgements, and the same policy reconciles them. A caller can also open a run, fetch the candidates over the API and send judgements of its own. Both are built, and their pages are not written yet.

## Not yet

- The reconciliation policy cannot be changed. A `policy.toml` in an entity type's directory is listed by `spool info` as not used by this version.
- There is no rule kind that says `unsure`. Only a strategy written in code, or a caller that sends its own judgements, can.
- Rules compare records of one entity type. There is no matching across types.
