---
title: Matching
description: Block rules pick the pairs worth comparing, match and no_match rules judge them, and a match places new records without moving the identities that exist.
---

Matching answers one question about two records: are they the same thing? In Spool the answer is a **judgement**: `match` or `no_match`. A third, `unsure`, can come only from a strategy written in code. A judgement is kept, and it changes nothing until a run turns judgements into identities.

This page covers the three kinds of rule, what a match does with their judgements, what that costs, and what to do when a rule gets better.

## Before you start

The examples use the sample project with both of its files of rows loaded and matched, which is where [Getting started](/docs/getting-started) ends. If you have that project and its server is running, use it. If not, this makes it:

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

{/* sample: background */}

```sh
spool dev
```

Leave that running. In a second terminal, in the `companies` directory:

```sh
spool load samples/crm-1.csv
spool match
spool load samples/crm-2.csv
spool match
```

## Three kinds of rule

A rule is a SQL file that holds one condition over two rows of the feature table, `l` and `r`. The file's name is the rule's name, and the directory it is in says what kind it is.

| Directory | What a rule there says |
| --- | --- |
| `rules/block/` | This pair is worth comparing. Pairs that no block rule finds are never compared. |
| `rules/match/` | This pair is the same thing. |
| `rules/no_match/` | This pair is not the same thing. It wins over every match rule. |

The sample project has one of each:

{/* sample: existing */}

```sql title="entities/company/rules/block/name_prefix.sql"
-- A block rule says which pairs are worth comparing: here, two names that
-- begin with the same four characters. `l` and `r` are two rows of the
-- feature table.
left(l.name_key, 4) = left(r.name_key, 4)
```

{/* sample: existing */}

```sql title="entities/company/rules/match/similar_name.sql"
-- A match rule says a pair is the same thing: here, two names that are
-- close. The similarity is 1 for equal names and 0 for names with nothing
-- in common.
jaro_winkler_similarity(l.name_key, r.name_key) >= 0.92
```

{/* sample: existing */}

```sql title="entities/company/rules/no_match/different_country.sql"
-- A no_match rule says a pair is not the same thing, and wins over any
-- match rule. This one holds only when both rows have a country.
l.country <> r.country
```

`name_key` is a [feature](/docs/concepts/entity-types-and-features): the name in lower case, with the space around it removed.

Block rules exist because comparing every record with every other does not scale. A block rule should be an equality, so that the database can find the pairs with a join. An equality over an expression is fine, as here. Write one file per equality: a block rule that says `OR` compares everything with everything.

For each pair the block rules find, the judgement is:

1. `no_match` if any no_match rule holds,
2. otherwise `match` if any match rule holds,
3. otherwise no judgement at all.

## Empty values

A comparison with an empty feature is neither true nor false, as in SQL, so a rule that is only that comparison does not hold. Two records without a country are not kept apart by `l.country <> r.country`.

In a rule with `AND`, `OR` or `NOT`, say what an empty value should mean with `coalesce`: `coalesce(l.country = r.country, false)` holds only when both have a country and they are equal, and `NOT coalesce(l.country <> r.country, false)` holds unless both have a country and they differ.

## What a match does

`spool match` starts a run. A run has a scope: the records of one entity type that are new since the last run of that type that succeeded, plus any that an earlier run left for review. It compares new records with each other and with the ones that are placed. It does not compare two records that are both placed.

It then turns the judgements into identities. The rules for that are fixed, and there is no setting for them:

1. A new record that matches members of exactly one identity, with no `no_match` against it, joins that identity.
2. New records that match only each other form a new identity.
3. A new record that matches members of two or more identities is left without an identity, and a [review item](/docs/concepts/review) is recorded.
4. Identities that exist are never merged or split by a run.

```csv title="crm-3.csv"
c-11,The Halden Group,GB
```

## The cost of IDs that stay

Rule 4 is the reason an ID can be stored somewhere else and trusted. It also makes the result depend on the order rows arrive in. Two records that arrive together and match become one identity. The same two, each placed alone before a rule matched them, stay apart until someone merges them.

So a better rule does not repair old data by itself. The next section shows what it does instead.

## Rules that get better

`crm:c-11` should have joined Halden Group. Make the transform drop a leading "the":

```sql title="transforms/name_key.sql"
-- Lower case, without the space around it or a leading "the".
lambda name: regexp_replace(lower(trim(name)), '^the ', '')
```

`spool dev` computes the features again. No identity changes, because both records are placed. To see what the better rule says about records that are placed, match again with `--rematch`, which compares every record of the type:

```sh
spool match --rematch
```

```text title="Output"
run         10, type `company`
examined    0 records without an identity and every record placed before, 15 candidate pairs
judgements  11 match, 3 no_match
placed      0 records, 0 identities created
suggested   1 merge, 0 splits: `spool show runs 10` lists them
```

The run placed nothing and moved nothing. It reports a **suggested merge**: two identities with matches between their members. A person or an agent who agrees merges them, which [Identities](/docs/concepts/identities#merge) shows. A rematch reports suggested splits the same way, when a no_match rule holds between two members of one identity.

A better matcher run over old data produces a list of suggestions, not a change to IDs that other systems have stored.

The suggestions are part of the run's report and are not kept as review items. `spool show runs <run>` lists them for any run, and `GET /v1/runs/<run>` has them as JSON. Nothing sorts or pages them, so a rule change that suggests thousands of merges gives a report of thousands of lines.

## Recompute

A rematch says where the rules disagree. It does not say what the identities would be. `spool recompute` does: it matches every record again, all at once, by the rules as they are now, as a new store would, and sets the result against the identities there are. It changes nothing.

```sh
spool recompute
```

```text title="Output"

unchanged  5 identities would keep exactly their records
merged     1 identity would take records from more than one; 1 identity merged into another, its ID standing for it
gain       1 identity would gain records
moved      1 record would change identity
pairs      11 pairs share an identity now, 12 would after, 11 of them both

1 change, the largest first
#  kind   records  identity                              now                                     after
1  merge  2        01a1f145-fe9f-7341-9090-282ac5e8045e  Halden Group (1), The Halden Group (1)  Halden Group (2, keeps its ID, 1 identity merged in)
`--identity <id>` shows a change record by record

plan  43b0bfe383ba9c04: nothing was changed. `spool recompute --apply 43b0bfe383ba9c04` applies it
```

The summary comes first. **pairs** is one number for how far apart the two groupings are: pairs of records that share an identity now, after, and both. Then come the changes, the largest first. A change is the identities of now and after that share records. Its kind is `split`, `merge`, `regroup` (several into several), `gain`, `lose` (records that would wait for review), `new` or `review` (every record would wait). Ten are listed, `--detail` lists all of them, and `--limit` and `--offset` page them, so a project with a hundred thousand records starts with the identities that change most.

`--identity` shows one change record by record:

```sh
HALDEN=$(spool show records crm:c-5 | awk '/^identity/ {print $2}')
spool recompute --identity $HALDEN
```

```text title="Output"
2c53c39b-ba40-34f1-5a6c-f335adbe639c  crm:c-11        The Halden Group  01a1f145-ff2f-7340-b100-9d437f81cfac  1

```

Which identity keeps its ID follows the rule a split follows. An identity keeps its ID with the group that gets most of its records. Where several identities have their most in one group, the one with the most records there keeps its ID, the older one on a tie, and the others are merged into it, so that a system that stored their IDs still finds the entity. A group in which no identity has its most is a new identity.

Applying is a separate step, and it takes the plan:

```sh
spool recompute --apply 43b0bfe383ba9c04 --reason "names without a leading the"
```

```text title="Output"
type        `company`, match run 12, reconcile run 13
changeset   at log position 4, by the engine: `spool show log` has it
identities  6 now, from 7: 0 made, 1 merged away
records     1 moved, 0 placed, 0 left an identity

applied plan 43b0bfe383ba9c04
```

It works the result out again and refuses if it is not that plan, so what is applied is what was shown: if rows were loaded, rules changed or identities moved in between, it says so and changes nothing. A match run judges every record and keeps its judgements, as any run does, and the changes are one changeset in the log. The engine is its author, because the rules decided it, and the run is recorded as started by whoever applied. `POST /v1/changesets/<seq>/undo` takes it back like any other changeset.

What people decided counts for more than the rules, and [Review](/docs/concepts/review#recompute-and-what-people-decided) says how. In short: a `must_link` or a `cannot_link` holds, records a person or an agent put together stay together, records a reviewer dismissed stay without an identity, and records their source took back are left out. Where the rules join a group and something in it says two of its records differ, the group waits for review without an identity, as new records do after a match.

Nothing recomputes by itself. A rule change alone still moves no identity.

## Other ways to judge

SQL rules are the built-in strategy. A project can also hold strategies written in Python or TypeScript under `entities/<type>/strategies/`, which the server runs as child processes with `uv` or `bun`. They read candidate pairs and write judgements, which may be `unsure`, and the same four rules turn them into identities. The repository's [`benchmarks/resolution/people`](https://github.com/alexpatow/spool/tree/main/benchmarks/resolution/people) project has a strategy that runs Splink.

A caller can also open a run, fetch the candidates over the API and send judgements of its own. [The HTTP API](/docs/api#runs) lists the calls.

## What matching does not do

- The four rules that turn judgements into identities cannot be changed.
- A recompute runs the SQL rules. A strategy written in code cannot be recomputed.
- No SQL rule says `unsure`. A pair is matched, kept apart, or not judged.
- A rule sees the features of two records and not their sources. It cannot say that one source never holds the same thing twice.
- Rules compare records of one entity type.

[Limits](/docs/limits) has the rest.
