---
title: Identities
description: An identity is a minted ID and the records that belong to it. IDs are never reused, and every change, including merges, splits and undos, is a changeset in an append-only log.
---

An **identity** is one real-world thing as Spool knows it: an ID, an entity type, and its records. The ID is what other systems store.

This page covers the guarantees every identity has, then walks through a merge, a merged ID that still resolves, an undo, a split and a constraint. Every step is a call you can paste.

## Before you start

The examples pick up where [Getting started](/docs/getting-started) leaves off, with both CSV files loaded and matched. If that server's still running, use it. Otherwise:

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

{/* sample: background */}

```sh
spool dev
```

Leave it running. In a second terminal, in `companies`:

```sh
spool load samples/crm-1.csv
spool match
spool load samples/crm-2.csv
spool match
```

Then load two more rows, which the examples below correct:

```csv title="crm-3.csv"
id,name,country
c-10,Acorn Tooling,GB
c-11,The Halden Group,GB
```

```sh
spool load crm-3.csv
spool match
```

Acorn Tooling joined Acorn Tools because the names are close. The Halden Group got its own identity because the block rule compares the first four letters. [Matching](/docs/concepts/matching#what-a-match-does) explains both.

## What an identity is

Identity IDs are minted, so yours differ from the ones here. The commands keep each ID in a shell variable, so you can paste them as is:

```sh
ACORN=$(spool show records crm:c-1 | awk '/^identity/ {print $2}')
spool show identities $ACORN
```

An identity has no attributes of its own: no name, address or "golden record". It's a set of records, and each record keeps what its source said. An identity is displayed by its records' most common label.

Every identity guarantees three things:

- **The ID is minted, not derived.** It's a UUID created with the identity. It doesn't depend on the records or the rules, so a better rule can't change it.
- **The ID is never deleted or reused.** An identity merged into another remains as a pointer to the survivor.
- **A record belongs to at most one identity.** Belonging to none means nothing has placed it yet.

## The log

Identities change in exactly one way: a **changeset** is committed. A changeset is an ordered list of operations with an author and a reason, applied atomically. The changeset log is the source of truth.

```sh
spool show log
```

```text title="Output"
POSITION  ACTOR   OPERATIONS  FROM             STARTED BY                                 REASON
1         engine  10          reconcile run 3  user:01a1f0a0-9920-7253-869c-3c01d1dee766  reconcile new records
2         engine  4           reconcile run 6  user:01a1f0a0-9920-7253-869c-3c01d1dee766  reconcile new records
3         engine  3           reconcile run 9  user:01a1f0a0-9920-7253-869c-3c01d1dee766  reconcile new records
```

So far, matches wrote every changeset. `actor` says who committed it: `engine` for a run, `user:<id>` for a person, `agent:<name>` for a token. `started by` says who started the run or made the call behind it. Under `spool dev`, that's always its one built-in account.

There are six operations: `create_identity`, `assign`, `merge`, `reinstate`, `constrain` and `unconstrain`. [The HTTP API](/docs/api#changesets) documents each. Every operation states what it expects, and that's checked on commit. An `assign`, for example, names the record's current identity as `from`, and is rejected if the record has moved since. A changeset that fails a check is rejected whole, and the response names the operation.

People and agents write changesets too, with `POST /v1/changesets`, in the studio, or with the [MCP](/docs/mcp) tool `commit_changeset`. They pass the same checks as a run's.

## Merge

The Halden Group and Halden Group, both in GB, are one company. A merge is a changeset with one operation:

```sh
HALDEN=$(spool show records crm:c-5 | awk '/^identity/ {print $2}')
THE_HALDEN=$(spool show records crm:c-11 | awk '/^identity/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/changesets -d '{"reason": "The Halden Group is Halden Group", "ops": [{"op": "merge", "from": "'$THE_HALDEN'", "into": "'$HALDEN'"}]}'
```

```text title="Output"
{"seq":4,"changeset":"01a1f0a8-1fd6-7793-a34a-135f4d04c290","content_hash":"f61c94ca42fcef2f989c85ee67d3fb1af3b99c9e36dda9edc7246f3246fa01ef"}
```

`seq` is its log position. `crm:c-11` now has `crm:c-5`'s identity:

```sh
spool show records crm:c-11
```

```text title="Output"

type      company
source    crm
key       c-11
loaded    2026-11-18T21:46:59Z by run 7
identity  01a1efc6-41cd-775d-8758-e7329447fd9a

payload

  name     The Halden Group
```

## Undo

An undo is a new changeset the server derives from the log. History isn't rewritten. The merge is the last line of `spool show log`, so undo it by position:

```sh
MERGE=$(spool show log | tail -n 1 | awk '{print $1}')
curl -s -X POST http://127.0.0.1:7765/v1/changesets/$MERGE/undo -d '{"reason": "merged too early"}'
```

```text title="Output"
{"changeset":{"id":"01a1f0a8-202a-75f9-b4b0-6a8302b02c94","base":4,"actor":"user:01a1f0a0-9920-7253-869c-3c01d1dee766","reason":"merged too early","run":null,"ops":[{"op":"reinstate","identity":"01a1f0a0-99e2-71d0-a422-eb2cb5f32303"},{"op":"assign","record":"2c53c39b-ba40-34f1-5a6c-f335adbe639c","from":"01a1efc6-41cd-775d-8758-e7329447fd9a","to":"01a1f0a0-99e2-71d0-a422-eb2cb5f32303"}]},"committed":{"seq":5,"changeset":"01a1f0a8-202a-75f9-b4b0-6a8302b02c94","content_hash":"7fba583a5b6fef12c438a1234d45f3f37e496271fbacfe3e9d9651dae8ce3684"}}
```

```sh
spool show records crm:c-11
```

The merged-away identity is active again under its original ID, with its record back. An undo is checked against the current state. If later changes mean it no longer applies, it's rejected, and nothing is half-undone. With `"commit": false`, the call just returns the changeset the undo would commit.

## Split

Say Acorn Tooling isn't Acorn Tools. There's no split operation: a split is a new identity plus the `assign` operations that move records into it, in one changeset. Name one side's record IDs and the server writes the changeset:

```sh
TOOLING=$(spool show records crm:c-10 | awk '/^record/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/identities/$ACORN/split -d '{"records": ["'$TOOLING'"], "reason": "Acorn Tooling is another company"}'
```

The larger side keeps the ID, and on a tie the side you didn't name keeps it, so Acorn Tools kept its identity and `crm:c-10` moved to a new one. The split also recorded a `cannot_link` between the sides, so a later match can't rejoin them. Pass `"keep_apart": false` to skip it.

A system that stored Acorn's ID for `crm:c-10` now holds a stale one. It learns about the split from the log, as [Using the IDs](/docs/using-the-ids#follow-the-log) shows.

## Constraints

A constraint is a decision that outranks the rules. `cannot_link` means no changeset may put two records in one identity, and `must_link` means they must share one. A match treats a constraint as a winning judgement: `must_link` reads as `match` and `cannot_link` as `no_match`.

A rule keeps the two Halden Groups apart today. A constraint keeps them apart whatever the rules become:

```sh
GB=$(spool show records crm:c-5 | awk '/^record/ {print $2}')
US=$(spool show records crm:c-6 | awk '/^record/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/changesets -d '{"reason": "separate legal entities", "ops": [{"op": "constrain", "kind": "cannot_link", "a": "'$GB'", "b": "'$US'"}]}'
```

```text title="Output"
{"seq":7,"changeset":"01a1efa5-8358-743c-9fc6-fac999fdaa4f","content_hash":"9b1ab005c425ddd81c5b1ee95101788266b244020147781da5cd9d0ce4c8f5e4"}
```

Any changeset that would break a constraint is rejected, whoever wrote it. Try to merge the two:

```sh
HALDEN_US=$(spool show records crm:c-6 | awk '/^identity/ {print $2}')
curl -s -X POST http://127.0.0.1:7765/v1/changesets -d '{"reason": "one group", "ops": [{"op": "merge", "from": "'$HALDEN_US'", "into": "'$HALDEN'"}]}'
```


## What doesn't change an identity

- Loading rows. New records have no identity until a match or changeset places them.
- Changing features, transforms or rules. Features are recomputed, and IDs stay.
- A rematch. It reports suggestions.
- A recompute, until applied. Applying it is an engine changeset in the log, like a match's.
- Retracting a row. The record leaves, and the identity keeps its ID. If nothing then holds the remaining records together, a [review item](/docs/concepts/review#a-possible-split) asks whether to split. Nothing splits automatically.

## Working with identities

- Merges, splits and constraints are HTTP calls, studio actions or MCP tools.
- Calls that change an identity take its ID, and changesets name records by record ID. Look them up first, as above.
- Identities have no computed attributes, only a label.
- Identities are never deleted.
