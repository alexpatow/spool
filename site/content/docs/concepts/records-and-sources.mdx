---
title: Records and sources
description: A record is a row as its source sent it, or a mention an extractor found in text. Records are immutable, a changed row becomes a new version, and a row its source drops can be retracted.
---

A **record** is one thing a source said, kept exactly as it arrived. Records come from two places:

- **Rows.** A **source** is where rows come from: a CRM export, a company registry, a warehouse table. Each row becomes a record.
- **Text.** A document is stored as is, and an **extractor** finds where it names something. Each of those places becomes a record. Extractors are your own Python or TypeScript, run by the server as child processes.

Either way, the same rules match them. This page covers what Spool keeps of a row, what happens when a row is reloaded, changed, retracted or rejected, and how records come out of text.

## Before you start

The examples pick up where [Getting started](/docs/getting-started) leaves off, with both CSV files loaded and matched. If that server's still running, use it. Otherwise:

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

{/* sample: background */}

```sh
spool dev
```

Leave it running. In a second terminal, in `companies`:

```sh
spool load samples/crm-1.csv
spool match
spool load samples/crm-2.csv
spool match
```

## A source is a file

Each source is a YAML file under `sources/`, named for the source. It lists the columns a row can have and which one is the key. Here's the one `spool init --example companies` wrote:

{/* sample: existing */}

```yaml title="sources/crm.yaml"
# A source of rows. `key` is the column that tells one row from another, and
# `columns` is every column a row may have.
key: id
columns: [id, name, country]
```

Add a column to it:

```yaml title="sources/crm.yaml"
key: id
columns: [id, name, country, website]
```

`spool dev` applies it on save. Rows loaded earlier stay as they were, with no value for the new column.

A source doesn't say what its rows mean. Which entity type they describe, and how they're compared, is in the entity type's [mapping](/docs/concepts/entity-types-and-features).

## What a record holds

```sh
spool show records crm:c-1
```

```text title="Output"
record    ab8e9d59-0aaa-96b9-ddb7-db0bff7a9356
type      company
source    crm
key       c-1
loaded    2026-11-18T21:43:51Z by run 1
identity  01a1efc6-41cd-775d-8758-e7300637659a

payload
  country  GB
  id       c-1
  name     Acorn Tools
```

- **`record`** is the record's ID, derived from source, key and content, so the same row gets the same ID on any machine. The one exception is a version that repeats earlier content: its ID derives from that content's ID and the version it follows.
- **`payload`** is the row as sent. Spool never rewrites it. Features are computed from it, and recomputed when you change how.
- **`identity`** is the identity the record belongs to, once a match places it.

Refer to a record by its ID, or as `source:key` for the latest version of that row.

## Loads are idempotent

A pipeline can send everything it has, every time. A row whose content matches what the server holds for its key is counted and skipped:

```sh
spool load samples/crm-1.csv
```

```text title="Output"
loaded  6 rows into source `crm`, type `company`: 0 new, 6 already held
```

## A changed row is a new version

A row with a known key and new content becomes a new record that replaces the earlier one. Save a file with `c-4` again, now with a website:

```csv title="changed.csv"
id,name,country,website
c-4,Larkfield Logistics,GB,https://www.larkfield.example
```

```sh
spool load changed.csv --source crm
```

```text title="Output"
loaded  1 row into source `crm`, type `company`: 0 new, 1 new version of a row held before
next: `spool match` places it in an identity
```

```sh
spool show records --source crm --key c-4 --ids --all-versions
```

```text title="Output"
RECORD                                SOURCE AND KEY  NAME                 IDENTITY                              VERSION
4b1bc703-9041-0989-d0eb-4df5e9eae0f2  crm:c-4         Larkfield Logistics  01a1efc6-41cd-775d-8758-e733aa086f7d  replaced
69c75f0d-bc65-b5f2-39aa-5c6d017a1531  crm:c-4         Larkfield Logistics  -                                     current
1 record has no identity: `spool match` places new records in identities, and `spool show review` lists the ones a match left out
```

Both versions are kept. `--all-versions` shows the replaced one, which lists otherwise hide. The new version has no identity yet. The next match gives it the identity of the version it replaces, whatever the rules say about the pair:

```sh
spool match
```

```sh
spool show records --source crm --key c-4 --ids --all-versions
```

```text title="Output"
RECORD                                SOURCE AND KEY  NAME                 IDENTITY                              VERSION
4b1bc703-9041-0989-d0eb-4df5e9eae0f2  crm:c-4         Larkfield Logistics  01a1efc6-41cd-775d-8758-e733aa086f7d  replaced
69c75f0d-bc65-b5f2-39aa-5c6d017a1531  crm:c-4         Larkfield Logistics  01a1efc6-41cd-775d-8758-e733aa086f7d  current
```

The earlier version stays in the identity and later records can still match it. That keeps history intact. It also means an old version missing a value can match something the new one wouldn't. [Review](/docs/concepts/review#a-conflict) shows what a missing value does.

A row's versions travel together. When the latest version is placed, by a match or by a changeset from a person or agent, earlier versions in other identities (or none) move with it. The moves are part of the same changeset, so the log shows them and an undo puts each version back. A match that moved some says `1 earlier version moved along` on its `placed` line. Splits, undos and approved drafts move only the records they name.

A row that changes from A to B and back to A ends at A. The second A is a new version with its own ID that replaces B. So a file is only skipped if it matches what the server holds now. Loading an older file after a newer one rolls the changed rows back to the older values.

## A row the source no longer holds

`spool retract` retracts a row. Name the source, the entity type and the key:

```sh
spool retract --source crm --type company c-9 --reason "deleted in the CRM"
```

```text title="Output"
run 11: 1 key named, 1 record taken back
1 record left an identity, by the changeset at log position 4
```

```sh
spool show records crm:c-9
```

```text title="Output"
record    34c3d52d-e53b-1559-7404-1892fb1fd4e3
type      company
source    crm
key       c-9
loaded    2026-11-18T21:43:51Z by run 4
identity  none: its source took it back in run 11

payload
  country  GB
  id       c-9
  name     Acorn Tool
```

The record left its identity, and later matches ignore it. The identity keeps its ID and other records. The row stays in the store. Loading the same key again, changed or not, restores every version.

Over HTTP, it's `POST /v1/retract` with `{"source": "crm", "entity_type": "company", "keys": ["c-9"]}`.

If the retracted row was what joined two other records of its identity, the identity isn't split. A review item asks whether it's still one thing. [Review](/docs/concepts/review#a-possible-split) has an example.

## What's rejected

A row with a column its source doesn't list fails the whole load. Here the rows go over HTTP as JSON, which `POST /v1/load` also accepts:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/load -d '{"source": "crm", "entity_type": "company", "rows": [{"id": "c-10", "name": "Acorn Hardware", "city": "Leeds"}]}'
```

```text title="Output"
{"error":{"code":"invalid","message":"load rejected: the rows have a column `city`, which sources/crm.yaml does not list. It lists `id`, `name`, `country`, `website`. Add the column to that file to keep it, or leave it out of the rows"}}
```

Rows are also rejected when their source has no file, or the entity type has no mapping for it. A missing column is fine: it's empty for that record.

## Records from text

A document is stored as it arrived, like a row. An extractor reads it and reports each place it names something. Each place becomes a record of the document's source, with the document and character range as evidence. From there it's a record like any other: immutable, placed by a match, and explainable.

```sh
spool extract samples/notes-1.txt
```

```text title="Output"
source     notes
read       1 document from samples/notes-1.txt
loaded     1 new, 0 already held, 0 new versions
extractor  companies
found      3 records in 1 document: 3 new, 0 already held

  company  Acorn Tools Ltd          notes:notes-1.txt[54-69]
  company  Larkfield Logistics Ltd  notes:notes-1.txt[119-142]
  company  Brightwater Foods Ltd    notes:notes-1.txt[179-200]
next: `spool match` places them in identities
```

[Extraction](/docs/concepts/extraction) covers it in depth, with extractors in Python and TypeScript.

## Where records come from

- `spool load` reads CSV and TSV files. See [the command line](/docs/cli#spool-load).
- `POST /v1/load` takes CSV, JSON or an Apache Arrow stream. See [the HTTP API](/docs/api#load-rows).
- Agents load rows with the MCP tool `load_rows`. See [MCP](/docs/mcp).
- `spool extract` stores text files as documents and runs an extractor. Over HTTP that's `POST /v1/documents` and `POST /v1/extractions`, and over MCP `load_documents` and `run_extraction`.
