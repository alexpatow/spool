---
title: Entity types and features
description: An entity type is a directory that declares what its records are compared by, and how each source's columns become those features. Built here from an empty project, as a product catalog fed by two suppliers.
---

An **entity type** is a kind of thing you want one ID for: a company, a person, a product. Spool ships none. Each project declares its own, so two projects can disagree about what a product looks like.

A **feature** is a value records of that type are compared by. Sources name and format their columns differently, so rules never read raw rows. They read features, and every source maps onto them.

This page builds a project from nothing: a product catalog fed by two suppliers, which write the same products differently.

## Start an empty project

{/* sample: new session */}

```sh
spool init catalog
cd catalog
```

{/* sample: background */}

```sh
spool dev
```

Leave that running, and open a second terminal in `catalog`. `spool dev` applies each file below as you save it.

## Declare the sources

Each source is a YAML file under `sources/`, named for the source. It lists the columns a row can have and which one is the key. Northwind sends a product catalog:

```yaml title="sources/northwind.yaml"
key: sku
columns: [sku, title, brand, model, gtin]
```

Harbor sends the same kinds of products under different column names, with EAN-13 barcodes where Northwind has 12-digit UPCs:

```yaml title="sources/harbor.yaml"
key: item_id
columns: [item_id, description, manufacturer, mpn, ean]
```

## Add transforms

A transform is a file under `transforms/`, named for the transform. It holds `lambda`, its argument names, and one DuckDB expression:

```sql title="transforms/gtin14.sql"
-- UPC-A (12 digits) and EAN-13 (13 digits) as one 14-digit GTIN, or nothing.
lambda code: nullif(lpad(regexp_replace(coalesce(code, ''), '[^0-9]', '', 'g'), 14, '0'), '00000000000000')
```

```sql title="transforms/model_key.sql"
-- "K2-BLK", "k2 blk" and "K2BLK" all become "K2BLK".
lambda model: nullif(upper(regexp_replace(model, '[^A-Za-z0-9]', '', 'g')), '')
```

```sql title="transforms/brand_key.sql"
lambda brand: lower(trim(brand))
```

A transform sees the values of one record only, and can't read a table. Values arrive as text. What it returns sets the feature's type, so a transform that returns a date gives you a feature rules can compare as dates.

## Declare the entity type

`entities/product/` declares the entity type `product`. Its `entity.yaml` lists the features and maps each source onto them:

```yaml title="entities/product/entity.yaml"
label: title
features: [title, brand_key, model_key, gtin]

mapping:
  northwind:
    title: title
    brand_key: { from: brand, transform: brand_key }
    model_key: { from: model, transform: model_key }
    gtin: { from: gtin, transform: gtin14 }
  harbor:
    title: description
    brand_key: { from: manufacturer, transform: brand_key }
    model_key: { from: mpn, transform: model_key }
    gtin: { from: ean, transform: gtin14 }
```

- **`features`** are the columns of the type's feature table, which rules read.
- **`label`** is the feature a record is shown by.
- **`mapping`** says where each feature comes from, per source. `title: description` takes a column as is. `{ from: ean, transform: gtin14 }` passes it through a transform, and `from` can be a list for a transform with several arguments.
- A transform with no file in `transforms/` is the DuckDB function of that name, such as `upper`.
- A feature a source doesn't map is empty for that source's records. Every feature needs at least one source.

## Add rules

Rules live under the entity type. These compare candidates within a brand or with the same barcode, match on a barcode or a model number, and keep two different barcodes apart, because colour variants often share a model number:

```sql title="entities/product/rules/block/same_brand.sql"
l.brand_key = r.brand_key
```

```sql title="entities/product/rules/block/same_gtin.sql"
l.gtin = r.gtin
```

```sql title="entities/product/rules/match/same_gtin.sql"
l.gtin = r.gtin
```

```sql title="entities/product/rules/match/same_model.sql"
l.model_key = r.model_key
```

```sql title="entities/product/rules/no_match/different_gtin.sql"
l.gtin <> r.gtin
```

[Matching](/docs/concepts/matching) covers the three kinds of rule. `spool info` shows the project as Spool reads it:

## Changing a declaration

When `entity.yaml` or a transform it uses changes, Spool rebuilds the feature table from the stored rows, and `spool dev` prints `rebuilt product`. That works because records keep their rows as they arrived.

No identity changes. Identities hold records, not features, so every ID stays put, and records that are already placed aren't matched again. [Matching](/docs/concepts/matching#rules-that-get-better) covers what to do when a better feature would have matched differently.

## What's checked

Mistakes in these files are caught when the project is read, not when rows arrive. `spool info`, `spool build` and `spool dev` all reject:

- a mapping that names a source with no file,
- a column the source doesn't list,
- a transform given the wrong number of columns,
- a transform or rule DuckDB can't prepare.

Misspell `description` in Harbor's mapping:

```yaml title="entities/product/entity.yaml"
label: title
features: [title, brand_key, model_key, gtin]

mapping:
  northwind:
    title: title
    brand_key: { from: brand, transform: brand_key }
    model_key: { from: model, transform: model_key }
    gtin: { from: gtin, transform: gtin14 }
  harbor:
    title: descripton
    brand_key: { from: manufacturer, transform: brand_key }
    model_key: { from: mpn, transform: model_key }
    gtin: { from: ean, transform: gtin14 }
```

{/* sample: fails */}

```sh
spool info
```

```text title="Output"
error: ./entities/product/entity.yaml: mapping of `title` from `harbor`: `descripton` is not a column of sources/harbor.yaml
```

`spool dev` reports the same error on save and keeps running the last good version. Fix it:

```yaml title="entities/product/entity.yaml"
label: title
features: [title, brand_key, model_key, gtin]

mapping:
  northwind:
    title: title
    brand_key: { from: brand, transform: brand_key }
    model_key: { from: model, transform: model_key }
    gtin: { from: gtin, transform: gtin14 }
  harbor:
    title: description
    brand_key: { from: manufacturer, transform: brand_key }
    model_key: { from: mpn, transform: model_key }
    gtin: { from: ean, transform: gtin14 }
```

## Names

Source, entity type, transform and rule names come from file and directory names. Use lowercase letters, digits and underscores, starting with a letter. Entity type names can be up to 48 characters.

## Scope of a declaration

- Features are SQL expressions. A normaliser that needs a lookup table or a library runs before the rows are sent.
- Entity types are declared in project files, which `spool dev` applies on save and [`spool build` and `spool apply`](/docs/deploying) apply to a deployed server.
- Rules compare records of one entity type.
