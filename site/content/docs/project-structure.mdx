title: Project structure
description: Every file a Spool project can contain, with an example of each, the keys it takes, and how a file's path becomes its name.
---

A Spool project is a directory you keep in Git. It declares where records come from, what kinds of thing they describe, and how they're matched. `spool dev` reloads it as you save, and `spool build` compiles it into the single manifest a deployed server reads.

This is the reference for every file a project can contain, with an example and a link to the page that explains it. The examples come from `spool init --example companies`, plus one strategy it doesn't write. Without `--example`, `spool init` writes just the folders (each with a `.gitkeep`), `.gitignore`, `.env.example` and the coding-agent files.

{/* sample: new session */}

```sh
spool init companies --example companies
cd companies
```

## The directory

```text
companies/
├── sources/
│   ├── crm.yaml                    the source `crm`: its key and its columns
│   └── notes.yaml                  the source `notes`: what a record from a note may say
├── transforms/
│   └── name_key.sql                the transform `name_key`: one SQL expression
├── entities/
│   └── company/                    the entity type `company`
│       ├── entity.yaml             its features, and how each source maps onto them
│       ├── rules/
│       │   ├── block/              which pairs are compared
│       │   │   └── name_prefix.sql
│       │   ├── match/              which pairs are the same thing
│       │   │   └── similar_name.sql
│       │   └── no_match/           which pairs are not
│       │       └── different_country.sql
│       ├── strategies/             optional: matching written in Python or TypeScript
│       └── extract.md              optional: what an extractor is told about the type
├── extractors/
│   └── companies.py                the extractor `companies`: a Python file that asks a small model
├── samples/                        sample rows and a sample note. Not read by the server
├── AGENTS.md                       what a coding agent should know here. Not read by the server
├── CLAUDE.md                       imports AGENTS.md, for Claude Code
├── .agents/skills/                 skills that teach coding agents Spool
├── .claude/skills/                 a symlink to each of those, for Claude Code
├── .gitignore                      leaves out .spool/ and .env
├── .env.example                    the form of .env
├── .env                            yours: secrets for the project's code. Not committed
└── .spool/                         the development store and the compiled manifest. Not committed
```

## The path is the name

There's no registry. `entities/company/` declares the entity type `company`, `entities/company/rules/match/similar_name.sql` is its match rule `similar_name`, and `sources/crm.yaml` is the source `crm`. Rename the file and you rename the thing.

Use lowercase letters, digits and underscores, starting with a letter. Entity type names can be up to 48 characters.

## Source files

`sources/<source>.yaml`. Explained in [Records and sources](/docs/concepts/records-and-sources).

{/* sample: existing */}

```yaml title="sources/crm.yaml"
# A source of rows. `key` is the column that tells one row from another, and
# `columns` is every column a row may have.
key: id
columns: [id, name, country]
```

| Key | Meaning |
| --- | --- |
| `columns` | Every column a row can have. Rows with other columns are rejected. Required |
| `key` | The column that identifies a row. Required for row sources. Document sources have none: their records are keyed by position |
| `evidence` | A column of JSON text saying where a row was found, stored as the record's evidence and not compared. Optional |

Unknown keys are rejected.

{/* sample: existing */}

```yaml title="sources/notes.yaml"
# A source of documents: here, notes of calls. An extractor finds records in
# them, and `columns` is everything such a record may say.
columns: [name]
```

## Transform files

`transforms/<transform>.sql`. The word `lambda`, the argument names, and one DuckDB expression that turns column values into a feature. Lines starting with `--` are comments. A transform with no file is the DuckDB function of that name, such as `upper`. Explained in [Entity types and features](/docs/concepts/entity-types-and-features).

{/* sample: existing */}

```sql title="transforms/name_key.sql"
-- A transform is `lambda`, the names of its arguments, and a DuckDB
-- expression over them.
lambda name: lower(trim(name))
```

## Entity type files

`entities/<type>/entity.yaml`. Explained in [Entity types and features](/docs/concepts/entity-types-and-features).

{/* sample: existing */}

```yaml title="entities/company/entity.yaml"
# `features` is what records are compared by, and `label` is the feature a
# record is called by. `mapping` says, for each source, which column each
# feature comes from, and the transform it goes through if it needs one. A
# record found in a note has no country.
label: name
features: [name, name_key, country]

mapping:
  crm:
    name: name
    name_key: { from: name, transform: name_key }
    country: country
  notes:
    name: name
    name_key: { from: name, transform: name_key }
```

| Key | Meaning |
| --- | --- |
| `features` | The columns of the type's feature table, which rules read |
| `label` | The feature a record is displayed by |
| `mapping` | Per source, where each feature comes from: a column, or `{ from: <column>, transform: <transform> }`. `from` can be a list for multi-argument transforms. Unmapped features are empty for that source's records |

Unknown keys are rejected.

## Rule files

`entities/<type>/rules/<kind>/<rule>.sql`. One SQL condition over two rows of the type's feature table, `l` and `r`. The directory sets the kind. Explained in [Matching](/docs/concepts/matching).

| Directory | A rule there says |
| --- | --- |
| `rules/block/` | This pair is worth comparing |
| `rules/match/` | This pair is the same thing |
| `rules/no_match/` | This pair isn't the same thing. Beats every match rule |

{/* sample: existing */}

```sql title="entities/company/rules/block/name_prefix.sql"
-- A block rule says which pairs are worth comparing: here, two names that
-- begin with the same four characters. `l` and `r` are two rows of the
-- feature table.
left(l.name_key, 4) = left(r.name_key, 4)
```

{/* sample: existing */}

```sql title="entities/company/rules/match/similar_name.sql"
-- A match rule says a pair is the same thing: here, two names that are
-- close. The similarity is 1 for equal names and 0 for names with nothing
-- in common.
jaro_winkler_similarity(l.name_key, r.name_key) >= 0.92
```

{/* sample: existing */}

```sql title="entities/company/rules/no_match/different_country.sql"
-- A no_match rule says a pair is not the same thing, and wins over any
-- match rule. This one holds only when both rows have a country.
l.country <> r.country
```

## Extractors

`extractors/<name>.py` or `.ts`. An extractor finds records in documents. [Extraction](/docs/concepts/extraction) walks through the sample `extractors/companies.py` and writes one in each language.

The server runs `.py` files with [uv](https://docs.astral.sh/uv/) and `.ts` files with [Bun](https://bun.sh), as child processes.

`entities/<type>/extract.md` is prose describing the type and how to quote it, which an extractor can pass to an LLM. [Extraction](/docs/concepts/extraction#with-a-hosted-model) has an example.

## Strategies

`entities/<type>/strategies/<name>.py` or `.ts`. A strategy is matching in code, for what SQL can't express: a trained model, a library, a service call. It gets the features of new and known records and returns judgements, which Spool turns into identities with its usual fixed rules. A directory with the same name next to the file holds anything else it needs.

```py title="entities/company/strategies/same_key.py"
"""Judges two records a match when their name keys are equal."""

from spool import strategy


@strategy
def judge(features):
    rows = features.to_pylist()
    judged = []
    for new in rows:
        if not new["is_new"]:
            continue
        for other in rows:
            # Each pair once: a new record with every known one, and with every new one before it.
            if other["record_id"] == new["record_id"] or (other["is_new"] and other["record_id"] > new["record_id"]):
                continue
            if other["name_key"] == new["name_key"]:
                judged.append({"left_id": new["record_id"], "right_id": other["record_id"], "verdict": "match", "score": 1.0})
    return judged
```

`features` is an Arrow table with one row per record of the type: its features, `record_id`, `is_new`, and `identity_id` if placed. A judgement names two records and a verdict, `match`, `no_match` or `unsure`, with optional `score` and `detail`.

Start a match with the strategy's name to use it:

```sh
curl -s -X POST http://127.0.0.1:7765/v1/match -d '{"entity_type": "company", "strategy": {"name": "same_key"}, "wait_ms": 60000}'
```

## Secrets

**`.env`** sets environment variables for the project's extractors and strategies, such as a hosted model's API key. It stays out of Git (`spool init` adds it to `.gitignore`) and out of the image (`spool build` adds it to `.dockerignore`). Copy `.env.example` to `.env` and fill it in:

```text title=".env"
OPENAI_API_KEY=sk-...
```

Extractors and strategies run in the project directory with Spool's environment. Spool rereads `.env` each time it starts one, so changes need no restart. Variables already set in Spool's environment win, as do the ones Spool sets for the code. Spool's own token and Google client secret are never passed on. Values are never printed, and a bad line is reported by line number.

Each line is `NAME=value`, optionally prefixed with `export `. Quoted values (single or double) are taken as is, and unquoted values end before ` #`. Lines starting with `#` are comments. Spool doesn't read `.env` for its own settings: set `SPOOL_URL`, `SPOOL_TOKEN` and the rest in its environment.

## What Spool writes

**`.spool/`** holds build output and stays out of Git (`spool init` adds it to `.gitignore`). `spool dev` keeps its store there as `dev.duckdb`, with the accounts file beside it, and `spool build` writes the manifest there. [Deploying](/docs/deploying) covers `spool build` and `spool apply`.

[`spool reset`](/docs/cli#spool-reset) empties the development store. To also drop its accounts, stop `spool dev` and delete `.spool/`. The next `spool dev` recompiles the project and starts fresh. Your project files live outside `.spool/`, so nothing else is lost.

Every run records the hash of the manifest it ran with, so any judgement traces back to the project version that produced it. `spool info` and `spool dev` print that hash.

## Files for coding agents

`AGENTS.md`, `CLAUDE.md`, `.agents/skills/` and `.claude/skills/` are for coding agents such as Claude Code, Codex and Cursor. The server reads none of them. `spool init` writes them, and `spool update-skills` updates them to a later version's. [Coding agents](/docs/agents) covers what's in them and which agent reads what.

## What's ignored

Files in the project's directories that this version doesn't use are listed by `spool info` under `not used by this version` and have no effect. Files at the project root, such as a README, and `samples/` aren't read at all.

[The command line](/docs/cli) lists the commands that read a project.
