Spool keeps entity IDs stable while data keeps arriving, on one machine. That focus rules some things out.

## What it isn't for

- **One-off deduplication.** If you have one file and nothing stores the IDs, [Splink](https://github.com/moj-analytical-services/splink) or [dedupe](https://github.com/dedupeio/dedupe) is less to run.
- **Automatic matching after bulk loads.** [Add a single record](/docs/cli#spool-add) to match it to existing identities in one call using SQL rules. Bulk loads match in a separate run.
- **Streaming.** There's no Kafka or change-data-capture connector. Something else collects rows and sends them.
- **Clusters and multi-tenancy.** One process owns one [DuckDB](https://duckdb.org) file on one machine, and a store holds one project.
- **In-process use.** There are no Python or Node bindings. Your code calls the HTTP API.
- **Golden records.** Spool says which records are one thing. It doesn't build a merged "best" record or write back to your sources.
- **Matching without rules.** The built-in matcher runs SQL rules you write. To use a learned model, run it as a [strategy](/docs/concepts/matching#other-ways-to-judge): `benchmarks/resolution/people` runs Splink that way.

[Compared with other tools](/docs/compared) says when to pick each of those tools.

## The trade-off behind stable IDs

A match never merges or splits identities that exist. That's what makes an ID safe to store elsewhere, and it has three consequences:

- **Results depend on arrival order.** Two matching records that arrive together become one identity. If each was placed before a rule linked them, they stay apart until someone merges them.
- **Better rules suggest, they don't move.** `spool match --rematch` lists the merges new rules imply. `spool recompute` previews the full regrouping and applies it when you ask.
- **Old versions still count.** A replaced row stays in its identity and can still match, so a corrected row can raise a review item through its earlier version.

[Matching](/docs/concepts/matching#the-cost-of-ids-that-stay) shows the first two with rows.

## Not in 0.4.0

- **Platforms.** Linux on x86-64 or arm64 with glibc 2.34+, macOS on Apple silicon, and a container image. There are no Windows, Intel Mac or Alpine builds, and no Homebrew, apt or Cargo packages.
- **Connectors.** `spool load` reads CSV. The API takes CSV, JSON and Arrow. Nothing reads a database or a warehouse directly.
- **Document formats.** Documents are plain text. Convert PDF and HTML first.
- **Hard deletes.** `spool retract` takes a row out of its identity and out of matching, but the record stays in the store.
- **Scoped tokens.** A token has full API access and doesn't expire, though you can revoke it. People sign in with a password or with Google.
- **Agents.** Over MCP, an agent can't approve drafts, add people or create tokens. Claude and ChatGPT on the web sign in with OAuth, which needs a public HTTPS address. Spool registers them itself: in Claude, choose "Register automatically", not Claude's published identity. That agent has the approving person's access, and nothing narrower.
- **Corrections from the CLI.** Merge, split, undo and review decisions are HTTP calls, MCP tools or studio actions.
- **Push notifications.** Consumers poll the [changeset log](/docs/using-the-ids#follow-the-log). There are no webhooks.
- **Operations tooling.** There's no backup command: copy the store file while the server is stopped. There are no metrics or traces beyond `GET /healthz`. The store format can change before 1.0.
- **Bundled runtimes.** Extractors and strategies need `uv` for Python or `bun` for TypeScript on the server.
- **Request size.** API requests are capped at 256 MiB. MCP requests are capped at 4 MiB.

## Benchmarks

The built-in rules on public data. Each run loads and matches the whole set from empty, on four cores and 16 GB:

| Data | Records | Seconds | Peak memory | Pair precision | Pair recall |
| --- | ---: | ---: | ---: | ---: | ---: |
| North Carolina voters, five sources | 500,323 | 15 | 1.4 GB | 0.988 | 0.881 |
| North Carolina voters, five sources | 5,000,000 | 210 | 13.4 GB | 0.880 | 0.879 |
| MusicBrainz songs, five sources | 193,750 | 8 | 0.7 GB | 0.997 | 0.862 |
| MusicBrainz songs, five sources | 1,937,500 | 67 | 4.3 GB | 0.959 | 0.863 |

Memory grows with the number of candidate pairs, so your block rules set how far one machine goes. Precision falls as a set grows, because the same towns hold more people who look alike. Measure rules at the size you'll run them.

On changing data, the test was five sources of about 100,000 voters each. It then added 100,000 rows, retracted 50,000, rematched everything and resent 10,000. That took 216 seconds and 2.2 GB, and every record that wasn't retracted kept its identity.

The scenarios and method are in [`benchmarks/`](https://github.com/alexpatow/spool/tree/main/benchmarks), and `spool bench` runs them.
