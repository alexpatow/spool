Spool pulls records out of text and rows, decides which are the same real-world thing, and gives each thing an ID that stays the same as more arrive. Matching records that describe the same thing is called entity resolution, or record linkage. Spool does that, takes records from text as well as tables, and keeps the IDs stable.

New to the terms? [What the hell is Entity Extraction and Resolution?](/explained) walks through each step on the sample data.

## How the parts fit

Spool is one server, written in Rust, with its data in a single embedded [DuckDB](https://duckdb.org) file. A project, a Git repo of YAML and SQL files, tells it what to do.

1. **A project is a directory.** Sources, features, rules and extractors are files, and a file's path is its name. [Project structure](/docs/project-structure)
2. **Records come from rows or text.** Each row of a source becomes a record. Documents are stored, and an extractor finds where each one names something. Each of those places becomes a record too. Extractors are Python or TypeScript that the server runs as child processes, and the sample one uses a small local model. Records are immutable, and loads are idempotent. [Records and sources](/docs/concepts/records-and-sources), [Extraction](/docs/concepts/extraction)
3. **Records are compared by features.** Each source's columns map onto the features of an entity type you declare, such as `company`. [Entity types and features](/docs/concepts/entity-types-and-features)
4. **Rules judge pairs.** A match compares new records with known ones and records a judgement per pair: `match` or `no_match`. A rule is a SQL condition over two records. [Matching](/docs/concepts/matching)
5. **Judgements become identities.** New records join an identity or start one. A match never merges or splits existing identities. Every change is a log entry with an author and a reason, and every change can be undone. [Identities](/docs/concepts/identities)
6. **Hard cases wait for review.** A record that fits two identities, or an identity that may have come apart, goes to a person or an agent. [Review](/docs/concepts/review)
7. **Other systems store the ID.** They look it up by a row's source and key, and follow the log for merges and splits. [Using the IDs](/docs/using-the-ids)

Four interfaces reach the same server:

| | For | Page |
| --- | --- | --- |
| The CLI | Loading, extracting, matching, inspecting and explaining | [Command line](/docs/cli) |
| The HTTP API | Everything. The other three are clients of it | [HTTP API](/docs/api) |
| The MCP endpoint at `/mcp` | Agents that load data, look things up and make corrections | [MCP](/docs/mcp) |
| The studio, in a browser | Browsing, reviewing, merging, splitting and undoing | [Getting started](/docs/getting-started#look-at-it-in-a-browser) |

## Who it's for

- You maintain a list of companies, people or products fed by several sources, and other systems refer to them by ID.
- Some of what you know is in text: notes, articles, emails.
- You want to see why two records matched, and undo a wrong match without rebuilding everything.
- You want matching rules reviewed like code, in files, with history.
- People or agents make corrections, and every correction has to be attributed and reversible.
- You have thousands to millions of records. Spool has been benchmarked at 5,000,000 on one machine.

[Use cases](/docs/use-cases) goes through real scenarios, from venture capital data to agent memory.
