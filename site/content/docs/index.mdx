Spool decides which records are the same real-world thing, and gives each thing an ID that stays the same as more records arrive.

You have rows from several places that describe the same companies, people or products, written differently in each. You want one ID per company that other systems can store. You get more rows every day, and the ID you handed out yesterday must still mean the same company tomorrow, including after you improve the matching.

Spool is a server that does that. It is written in Rust, stores its data in one DuckDB file, and is driven by a directory of YAML and SQL files that you keep in Git.

## What it looks like

Three rows from a CRM, loaded and matched. The first two are one company, so they get one identity:

| Record | Name | Identity |
| --- | --- | --- |
| `crm:c-1` | Acorn Tools | `01a1ef26-…-c8ac4f2f4ba2` |
| `crm:c-2` | ACORN TOOLS | `01a1ef26-…-c8ac4f2f4ba2` |
| `crm:c-3` | Larkfield Logistics | `01a1ef26-…-c8adb9f7e0e2` |

The rule that matched them is a line of SQL in a file of the project, over two records `l` and `r`:

```sql
l.name_key = r.name_key
```

Later another spelling arrives. It joins the identity that exists, and that identity keeps its ID:

| Record | Name | Identity |
| --- | --- | --- |
| `crm:c-4` | Acorn tools | `01a1ef26-…-c8ac4f2f4ba2` |

[Getting started](/docs/getting-started) does exactly this, with commands you can run.

## How it works

1. **A project is a directory.** Sources, features and rules are files, and a file's path is its name. [Project structure](/docs/project-structure)
2. **Rows become records.** A record is a row as it arrived. It is never changed, and loading it twice does nothing. [Records and sources](/docs/concepts/records-and-sources)
3. **Records are compared by features.** Each source's columns are mapped onto the features of an entity type that you declare. [Entity types and features](/docs/concepts/entity-types-and-features)
4. **Rules judge pairs.** A run compares what is new with what is known and writes down a verdict for each pair. [Matching](/docs/concepts/matching)
5. **Judgements become identities.** New records join an identity or start one. Identities that exist are never merged or split by a run. [Identities](/docs/concepts/identities)
6. **Every change is in a log.** A merge, a split and an undo are entries in it, with an author and a reason.
7. **What cannot be decided waits.** A record that fits two identities is left for a person or an agent. [Review](/docs/concepts/review)

There is an HTTP API for all of it, a browser interface for looking at the data and making corrections, and a command line that shows and explains.

## Who it is for

- You maintain a list of entities that several sources feed, and other systems refer to those entities by ID.
- You want to read why two records were matched, and take a wrong match back without rebuilding everything.
- You want matching rules reviewed like code, in files, with a history.
- You have people or agents making corrections, and need every correction attributed and reversible.

## What it is not meant for

- **Deduplicating one file once.** If you will never see more data and nobody stores the IDs, a script or a library such as [Splink](https://moj-analytical-services.github.io/splink/) is less to run. Spool's work is keeping IDs stable over time.
- **Deciding one record at a time, fast.** Rows are loaded in batches and matched by runs. It is not a lookup service that answers in a request whether a new customer is a duplicate.
- **Matching without rules of your own.** The built-in matcher runs the SQL rules you write. There is no trained model in the box. A model can be plugged in as a strategy written in Python or TypeScript.
- **Master data management.** Spool says which records are one thing. It does not build a merged "golden record", choose the best address, or push corrections back to the sources.
- **Many tenants or many writers.** One server owns one store. It scales up on a bigger machine, not out across machines.
- **Embedding in your process.** There are no Python or Node bindings. Your code calls a server.

## Where it stands

Spool is early, and nothing is published: no release, no package, no container image. Today you build it from source, as [Getting started](/docs/getting-started) shows. No version has been released, so formats and the API can still change.

[Limits](/docs/limits) lists what it does not do yet. The source is at [github.com/alexpatow/spool](https://github.com/alexpatow/spool), under the MIT licence.
